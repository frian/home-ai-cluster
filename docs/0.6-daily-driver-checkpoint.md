# 0.6 Daily-Driver Checkpoint

Status: Investigation

Date: 2026-08-30

## Scope

This is a release-readiness checkpoint for the non-binding `0.6.0` theme. It
does not authorize a release, RFC, implementation, configuration, lifecycle
change, version change, or release-direction change. Candidate focus areas are
investigations, not a release checklist.

## 0.6 goal and exit condition

The goal is to remove repeated operator friction without making Home AI Cluster
(HAC) own external-service or runtime lifecycle. The exit condition is:

> An operator can leave HAC installed and use it repeatedly without
> reconstructing prototype-era command details for ordinary work.

This checkpoint applies a high bar: a possible convenience is not a blocker.
Only current evidence that ordinary repeated use cannot meet that condition
would block `0.6.0`.

## What changed during 0.6 development

The prior external-information investigation identified repeated long-option
ceremony. RFC-0091 subsequently added the installed short form:

```sh
hac external-information --plugin NAME QUERY QUESTION
```

The fully explicit form remains supported. The current guidance also makes the
ordinary model clear: start `hac local` once, then send repeated `chat`, `code`,
`summarize`, or `classify` requests. Static operation retains one
operator-owned declaration at an explicit stable path rather than recreating
proof-era values. The fixed-loopback browser is now consistently documented as
Chat, Summarize, Classify, and Code.

Subsequent ordinary CLI evidence identified a second small repeated-typing
issue. The completed sequence—investigation, RFC-0092, acceptance, then
implementation—added only root `-h`, `-f/--file`, `-d/--declaration`,
`-l/--label`, and `-j/--json`. Existing `-v/--verbose` and every long form
remain supported. This finite vocabulary adds no configuration, lifecycle,
routing, capability, runtime, network, or privacy behavior.

The SearXNG persistence investigation reached a bounded Outcome B: current
upstream persistence guidance does not establish a concise, maintained,
direct-HTTP `127.0.0.1:8888` service path. It correctly declined to invent a
unit, proxy, copied uWSGI configuration, container ownership, or HAC/plugin
lifecycle management.

## Remaining concrete friction

No current concrete documentation or implementation defect meeting the release
blocker standard was found.

The remaining manual acts are either intentional ownership boundaries or lack
evidence that they prevent ordinary repeated use: preparing an external runtime,
keeping the ordinary process available, resolving an occupied fixed port through
normal operator control, explicitly selecting an external-information plugin,
and operating optional SearXNG separately. They do not require knowledge of
historical proof launchers or prototype-only syntax; current documentation marks
historical material as evidence and gives the ordinary path directly.

RFC-0092 deliberately leaves specialized and authority-sensitive options
long-only; that bounded choice is not unfinished `0.6` work.

## Non-blocking deferred ideas

- A current upstream-supported direct-HTTP SearXNG persistent-service path may
  justify a later plugin README-only follow-up. Until that evidence exists,
  Outcome B remains the correct conclusion.
- General retained configuration, implicit plugin selection, and automatic
  external-information behavior remain separate architectural questions for the
  `0.8` configuration theme, not evidence-backed `0.6` requirements.
- Runtime/model lifecycle ownership and richer provider diagnostics would alter
  accepted ownership or privacy/error boundaries; no current evidence makes
  them release necessities.
- A supported low-friction Windows installation path belongs to the later `0.9`
  candidate focus, not this checkpoint.

## Exit-condition assessment

For ordinary local use, an operator can install HAC, prepare the independently
owned runtime once, start `hac local`, and use the documented ordinary CLI or
fixed-loopback browser repeatedly. The ordinary CLI additionally has the bounded
RFC-0092 short-option vocabulary. For explicit static use, the operator retains
the declaration and repeats documented role commands rather than rebuilding a
historical proof. Optional external information remains visibly optional and
explicit.

The evidence therefore supports the exit condition. It does not establish that
every future convenience is unnecessary; it establishes that no current
evidence-backed friction prevents an honest `0.6.0` daily-driver claim under
the stated, bounded goal.

## Outcome

### Outcome A — 0.6 exit condition is satisfied

The `0.6` goal is sufficiently met. Optional candidate work is not converted
into release requirements. Remaining improvements are deliberate boundaries,
insufficiently evidenced, or assigned to later release themes. In particular,
the SearXNG persistent-service Outcome B is respected rather than reopened, and
this checkpoint pulls no configuration architecture into `0.6`.

## Next step

The next repository action should be a focused `0.6` release-readiness audit,
not another feature investigation. It should verify release artifacts and the
accepted and documented ordinary contract, including RFC-0092
implementation/documentation consistency, ordinary CLI/help behavior, and
repository quality gates, without preparing the release in this investigation.
It should also explicitly resolve or explain the repeated local-versus-clean-CI
Aider test discrepancy: local full-suite runs observe no child invocation in
`test_missing_target_is_created_empty_after_prerequisite_and_not_rolled_back`,
while RFC-0092 focused tests and clean CI passed. This is a release-readiness
validation question, not evidence that the daily-driver exit condition failed.
