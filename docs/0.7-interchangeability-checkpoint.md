# 0.7 Interchangeability Checkpoint

Status: Investigation

Date: 2026-08-30

## Scope

This is a release-theme checkpoint and sanitized retained operator proof for
the non-binding `0.7.0` theme. It is not an RFC, architecture change,
implementation authorization, release preparation, or claim that `0.7.0` is
already release-ready.

## 0.7 goal and exit condition

The non-binding `0.7` theme is:

> Interchangeable / acquisition and integrations

Its canonical goal is to prove that accepted external boundaries are genuinely
independent of one provider or one proof integration. Its canonical exit
condition is:

> A second materially different integration can use an existing HAC boundary
> without changing cluster-facing concepts or turning that boundary into a
> generic plugin framework.

## Materially different integrations

Both integrations are separate packages with exact RFC-0078 entry points and
the unchanged callable:

```python
async acquire(query: str) -> list[dict[str, str]]
```

SearXNG exposes `searxng` to an operator-owned local service through a fixed
loopback provider hop. It has no provider credential at that first hop, and the
operator owns the service lifecycle. Tavily exposes `tavily` to a public
external HTTPS service with a plugin-owned `TAVILY_API_KEY`, no local
provider-service lifecycle, and exactly one bounded provider request under
RFC-0093.

Both return only concrete `title`, `url`, and `content` candidates to the
existing HAC caller. They do not share implementation code or a provider
abstraction.

## Sanitized operator proof

An operator performed a live proof on 2026-08-30. This retained record excludes
the API key, Authorization header, raw provider material, source values,
generated answer, account identifiers, and provider request identifiers.

### Direct Tavily plugin live acquisition

The merged Tavily plugin made one live acquisition for a deliberately
non-sensitive public Python 3.14 free-threading query. It succeeded with
exactly five candidate dictionaries. Only these UTF-8 byte-size observations
are retained:

| Candidate | Title | URL | Content |
| --------- | ----: | --: | ------: |
| 1 | 57 B | 44 B | 501 B |
| 2 | 59 B | 91 B | 489 B |
| 3 | 38 B | 60 B | 481 B |
| 4 | 65 B | 58 B | 431 B |
| 5 | 20 B | 34 B | 460 B |

This sample stayed comfortably within RFC-0077's per-field limits. Its largest
content value was 501 UTF-8 bytes, versus RFC-0077's 1,024-byte content limit.
It is evidence that the selected `chunks_per_source=1` request shape is
workable for this proof, not evidence that Tavily can never return a candidate
exceeding RFC-0077 limits. RFC-0077 validation remains authoritative, and the
plugin must not truncate or repair evidence. This one sample establishes no new
source-size policy.

### Installed entry-point interchangeability

The installed environment reported:

```text
HAC: 0.7.0.dev0
entry point: searxng -> home_ai_cluster_plugin_searxng.plugin:acquire
entry point: tavily -> home_ai_cluster_plugin_tavily.plugin:acquire
```

The same installed HAC caller discovered both separately packaged integrations
through the unchanged category-specific RFC-0078 entry-point group. This is
metadata/discovery proof only: installation still grants neither plugin
automatic network authority.

### End-to-end explicit HAC proof

The operator then explicitly invoked `hac external-information --plugin tavily
...` for the same non-sensitive Python 3.14 subject with a local Chat capability
available. The explicit Tavily acquisition succeeded; its candidate data passed
the existing RFC-0078 caller boundary and RFC-0077 validation; HAC sent the
existing source-grounded Chat request; and ordinary Chat routing produced a
local model response. No acquisition failure occurred.

Answer factual quality is a separate source/synthesis-quality concern, not
proof of acquisition-boundary correctness.

## What this proves

The retained evidence proves that:

- two materially different separately packaged integrations coexist under the
  same existing RFC-0078 category;
- Tavily required no new HAC capability, route, provider abstraction, generic
  plugin framework, provider-selection system, configuration framework, or
  automatic acquisition behavior;
- provider-specific HTTP, credential, and parsing behavior remains outside HAC
  core;
- the closed candidate representation and fresh RFC-0077 validation remain
  unchanged;
- explicit operator selection remains the network-authority boundary; and
- one end-to-end Tavily operation can reach ordinary source-grounded Chat
  through the existing HAC path.

This does not prove that every possible future provider can use RFC-0078.

## What this does not prove

This proof does not establish Tavily uptime, pricing, quota stability, or
service guarantees; universal RFC-0077 size compatibility for all Tavily
results; source factual correctness; generated-answer correctness; automatic
fallback; generic provider interchangeability beyond the accepted two-provider
evidence; credential/configuration architecture; ordinary Chat network
authority; research loops, retries, URL following, or broader browsing
behavior.

## Exit-condition assessment

The evidence directly meets the canonical exit condition.

### Outcome A — 0.7 interchangeability exit condition is satisfied

The second materially different integration uses the already accepted RFC-0078
boundary without changing cluster-facing concepts or turning it into a generic
plugin framework. The result is significant because the proof comes from
provider difference rather than added abstraction: local operator-owned SearXNG
and credentialed public Tavily remain different behind the same small seam.

This does not mean that `0.7.0` should be tagged immediately.

## Remaining release productization

Exit-condition satisfaction is distinct from public release readiness. Before
an honest public `0.7.0` release, remaining focused work should be evaluated as
productization rather than new architecture:

- make the Tavily plugin independently releasable and publish its first stable
  package if release-readiness proof passes;
- make the second supported acquisition option discoverable in ordinary HAC
  documentation, including its explicit credential/network-disclosure boundary
  and installation path; and
- perform a focused 0.7 release-readiness audit after those steps.

Adding unrelated features merely to make 0.7 appear larger would violate the
scope-control intent of the release direction. Retained canonical configuration,
implicit/default provider selection, automatic external-information fallback
for Chat, and any bounded automatic behavior are deferred 0.8 topics.

## Next step

The next repository work is not another HAC feature. It should be the
separately scoped Tavily-plugin release/productization sequence, followed by
minimal HAC integration documentation and then a 0.7 release-readiness audit.
