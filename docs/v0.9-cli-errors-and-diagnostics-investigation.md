# v0.9 CLI Errors and Diagnostics Investigation

Status: Investigation

## Purpose

This investigation audits the operator-visible error, diagnostic, output, and
exit behaviour of the ordinary `hac` facade before the 1.0 contract is frozen.
It does not change CLI behaviour, accepted RFCs, or documentation contracts.

The result is that the ordinary surface has a coherent, deliberately
non-uniform model: parser/input misuse, finite-operation failures, completed
negative observations, and foreground-process lifecycle failures are distinct
operator outcomes. No raw traceback or unbounded implementation detail was
found on the audited ordinary failure paths.

## Accepted boundaries

The audit was read against the current project foundations and the 1.0 release
direction, the command reference and canonical workflow, and the accepted RFCs
that define the relevant surfaces. In particular, this includes the root
facade; local, static-cluster, and compatibility processes; health, preflight,
and status; finite native request failure ownership and timeouts; Chat, Code,
Code File, Aider, summarize, and classify; external-information acquisition
and source-grounded Chat; runtime/static declarations; and retained
configuration (RFC-0031, RFC-0033, RFC-0036, RFC-0038, RFC-0041,
RFC-0045, RFC-0060 through RFC-0063, RFC-0067 through RFC-0069,
RFC-0072, RFC-0074, RFC-0077 through RFC-0079, RFC-0080, RFC-0085 through
RFC-0088, and RFC-0094 through RFC-0096).

The project remains local-first and privacy-first. This audit does not propose
a generic error framework, logging, retries, telemetry, configuration
machinery, or lifecycle ownership.

## Ordinary command inventory

The root facade exposes fourteen ordinary commands: `local`, `static-cluster`,
`compatibility`, `aider`, `external-information`, `chat`, `code`, `code-file`,
`classify`, `summarize`, `preflight`, `health`, `status`, and `config`.

`hac` itself writes its no-argument/help text and version to stdout with exit
0. An unknown root command is the intentionally compact `error: unknown
command` on stderr with exit 2. It otherwise delegates the remaining arguments
without catching `SystemExit`, so delegated stdout, stderr, and exit status are
preserved. Root tests prove unchanged delegated arguments and unchanged
delegated exit status. The special Chat help spelling is presentation-only;
ordinary Chat execution is still delegated unchanged.

## Error and exit-code model

| Outcome | stdout | stderr | Exit | Meaning |
| --- | --- | --- | --- | --- |
| Help, version, successful finite command | Result/help | Empty | 0 | Successful invocation or operation. |
| Root unknown command; bounded native input error | Empty | Bounded `error:` message | 2 | Invocation/input error. Native request clients intentionally suppress detailed argparse text as their accepted input boundary. |
| Ordinary argparse/configuration/declaration misuse | Empty | argparse usage plus diagnostic | 2 | Invocation or local declaration/configuration validation error; detailed syntax is useful here. |
| Finite operational failure | Empty | Bounded category message | 1 | Request/integration/filesystem operation did not complete. |
| Preflight incoherent report | Completed report | Empty | 1 | A valid report says the declared state is incoherent. |
| Health/status negative observation | Completed snapshot/report | Empty | 0 | The observation was constructed, even when it says unavailable, unreachable, missing, or probe-failed. |
| Foreground startup/lifecycle failure | Parser or Uvicorn-owned diagnostic | stderr | Owner-defined non-zero | Startup construction is parser-bounded; bind and later server lifecycle remain Uvicorn/OS-owned. |

This is not an attempt to make all exit 1 outcomes identical. In particular,
preflight's non-zero completed incoherence is not construction failure, and
health/status observations are not requests whose negative data should be
rewritten as command failure.

All ordinary parser help paths exit 0 and write to stdout. The custom native
boundaries intentionally replace usage with `error: invalid request input`:
the request may contain a prompt, source text, label set, selected file, or
plugin question, and the compact message avoids reflecting that material.

## Finite request commands

Chat, Code, summarize, classify, Code File, and external-information use the
same HAC-owned HTTP boundary: connection failure becomes `ordinary cluster
unavailable`; timeout becomes `ordinary request timed out`; other transport or
unexpected client failure becomes `ordinary request failed`; 422, 404, and 503
become rejection, capability-specific absence, and runtime-unavailable;
invalid successful bodies become `invalid cluster response`. All are stderr
and exit 1, with no usage text. Aider has a separate external-process boundary,
so its prerequisite and integration failures correctly use Aider-specific
messages rather than pretending they are cluster transport failures.

Interactive Chat and Code deliberately keep a process-owned conversation only
after a successful turn. Blank input and aggregate-limit failures do not mutate
it. A failed request, malformed result, EOF, and Ctrl-C return to or end the
prompt without a traceback; failed turns do not mutate retained conversation
context. Progress (`…`) and recoverable diagnostics go to stderr, while model
content remains stdout.

## Foreground and observational commands

`local`, `static-cluster`, and `compatibility` validate their selected
composition before handing a constructed ASGI application to Uvicorn. The
ordinary facade does not wrap Uvicorn: a port bind error or later server
lifecycle diagnostic is therefore correctly Uvicorn/OS-owned rather than a
misleading HAC request error. No persistent server or port was started for this
investigation.

Preflight has the accepted report-result distinction: it can successfully
render `status: incoherent` and exit 1, while inability to construct a report
is `error: unable to construct static preflight report` on stderr/1. Health
converts adapter probe exceptions into the completed `probe-failed` observation.
Status similarly represents remote `unreachable`, `request-failed`,
`invalid-response`, and local runtime observations as completed data. These
differences are intentional and should be retained.

## Configuration diagnostics

`config` is coherent with RFC-0094 and the recent recovery work. Parser misuse
uses normal argparse output/2. Invalid retained state is bounded (for example,
`error: invalid retained configuration`) without printing its path or content.
Whole `config reset` removes unloadable state without loading it and reports
success; targeted mutation/removal and `show` fail closed when the state cannot
be loaded. Read/save/remove OS errors are category messages, not raw exception
text. This is a D finding, not a reopening of retained configuration.

## Privacy and implementation leakage

Audited finite client and integration failures collapse HTTPX, Pydantic,
plugin, subprocess, retained-configuration, file, and response details into
bounded product messages. The inspected tests specifically assert absence of
private request/response and exception detail on representative Chat,
summarize, classify, and external-information paths. Broad catches at these
operator boundaries either implement that privacy boundary or turn a health
probe failure into observed state.

No realistic ordinary path was found that prints a Python traceback, raw HTTPX
exception, validation dump, credential, prompt, acquired source content,
retained JSON, or retained configuration path. Explicit successful verbose/JSON
output may intentionally contain result attribution, model names, or
source-grounded evidence; that is selected success output, not failure leakage.

## Documentation and test coverage

The command reference and canonical operator workflow correctly distinguish
preflight coherence, local health, and static status, including their different
negative-result semantics. Existing focused tests strongly lock the native
safe-error vocabulary, stdout/stderr separation, parser/help output, facade
delegation, interactive recoverability, configuration reset, and observation
states.

### Findings

1. **Priority 6 — C: facade diagnostic integration coverage.** The root tests
   prove argument forwarding, help, and propagated `SystemExit`, but do not run
   an end-to-end delegated parser error and a real delegated operational failure
   through the facade while asserting their exact stdout/stderr pair. The code
   is direct delegation and no defect was observed. Add two focused facade tests
   when touching the facade again; no implementation change is warranted.

2. **Priority 6 — C: foreground server-owned diagnostic coverage.** Parser and
   pre-Uvicorn construction paths are covered, but this audit found no focused
   test that documents the intentionally Uvicorn-owned bind/startup terminal
   diagnostic boundary without binding an ordinary port. A mocked Uvicorn seam
   could record that ownership if the project needs a frozen test contract.

3. **Priority 6 — C: documentation is clear at the model level but lacks a
   single exit-code lookup.** Current documentation explains the important
   preflight/health/status distinctions, but does not consolidate the 0/1/2
   model for scripting. A future documentation-only update could link a compact
   version of this table from the command reference, subject to review.

4. **Priority 7 — D: differing parser detail is intentional.** Ordinary
   argparse-led topology, runtime, and configuration mistakes retain usage and
   detailed syntax; bounded prompt/source request commands collapse to the
   privacy-safe native input message. They have different accepted boundaries,
   so this is not an inconsistency to flatten.

## Classification

There are no category A findings: no already-authorized behaviour correction
was evidenced. There are no category B findings: the audit does not identify a
new product or compatibility decision requiring an RFC. The three category C
items are coverage/documentation evidence only. All remaining apparent
differences above are category D and are sufficiently bounded for the 1.0
candidate contract.

## Recommended next steps

If desired, make one small tests/documentation-only follow-up: add the two
facade end-to-end error assertions, one mocked-Uvicorn ownership assertion,
and a compact exit-code lookup in user documentation. Do not combine that work
with a generic error rewrite or change successful observation semantics.

## Explicit non-recommendations

Do not introduce a universal error/result abstraction, exception hierarchy,
structured logging, telemetry, retry policy, daemon, configuration framework,
or a wrapper that rewrites Uvicorn diagnostics. Do not change health or status
negative observations into command failures, or preflight incoherence into an
undifferentiated construction failure.

## Conclusion

The ordinary `hac` diagnostic surface is predictable enough to serve as a 1.0
candidate contract. Its meaningful distinctions are already visible in output
channel and exit status, bounded failure vocabulary protects private details,
and the remaining work is evidence consolidation rather than behavioural
hardening.
