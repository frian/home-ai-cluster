# v0.9 Legacy and Compatibility Surfaces Investigation

Status: Investigation

## Purpose

This investigation classifies the executable surfaces shipped by the current
`0.9.0.dev0` package before the 1.0 product contract is frozen. It is not a
removal, deprecation, redirect, or command-design decision. `pyproject.toml`
is the inventory authority; accepted RFCs decide the intended role.

## Accepted boundaries

The ordinary operator namespace is the fourteen-command `hac` root, with
`home-ai-cluster` as its equivalent long spelling (RFC-0050 and RFC-0052).
RFC-0050 deliberately left accepted diagnostic, history, and proof utilities
outside that root; exclusion was not retirement. RFC-0075 later retired exactly
four proof-only installed names (`static-proof`, `automatic-proof`,
`fallback-proof`, and `phase-12-heterogeneous-receiver`). They are absent from
the current script table and remain historical evidence only.

The current standalone diagnostics and history tools are explicitly excluded
from RFC-0075. The retained standalone equivalents of ordinary root commands
also remain explicitly preserved. No accepted RFC authorizes changing any of
the currently installed names in this investigation.

Classification uses these current roles: **ordinary** (A), **compatibility**
(B), **historical/proof** (C), **internal/non-product** (D), and **unresolved**
(E). A compatibility classification means intentionally shipped but not the
preferred ordinary discovery path; it does not imply pending removal.

## Ordinary facade inventory

The current ordinary root exposes: `local`, `static-cluster`, `compatibility`,
`aider`, `external-information`, `chat`, `code`, `code-file`, `classify`,
`summarize`, `preflight`, `health`, `status`, and `config`.

These are all Category A candidate surfaces. `compatibility` remains ordinary
in this limited sense because it is the accepted bounded OpenAI-compatible
access process; its name does not authorize generic OpenAI API compatibility.
`aider`, `external-information`, and `code-file` remain bounded caller edges,
not general tool, provider, filesystem, or execution authority.

## Surface-by-surface assessment

The two roots are intentional aliases: RFC-0052 gives `hac` a short installed
spelling and current Getting Started calls `home-ai-cluster` the equivalent
long root. They dispatch the same implementation and are both ordinary.

The seven mapped standalone commands are direct implementations used by their
ordinary root subcommands. The command reference labels them retained and puts
ordinary checkout use first. They are therefore intentionally installed
compatibility spellings, not competing preferred workflows. Their standalone
`--help` naturally uses its installed program name; root forwarding presents
the root spelling, so ordinary help does not present the standalone name as the
preferred command.

The two explanation commands are finite explicit diagnostic operations, not
old proof launchers. Routing explanation is synthetic and performs no request;
actual-request explanation executes its own explicit local request path and is
the only writer of its limited request account. They are not facade aliases and
are correctly not inferred to be obsolete from their absence from `hac`.

Request history is an accepted, opt-in, bounded, prompt-free local capability
under RFC-0035. Its two commands inspect and clear only that history. The lack
of `hac history` or `hac clear-history` is intentional under RFC-0050 and
RFC-0075; adding either would be a product/RFC decision, not an asymmetry to
fix in this investigation.

## Documentation exposure

README and Getting Started use `hac` for ordinary operation; Getting Started
also truthfully identifies the long root as equivalent. The canonical workflow
uses `hac`. The command reference makes `hac` / `home-ai-cluster` the ordinary
forms and presents the seven direct standalone equivalents only in a
repository-checkout mapping for compatibility or reference. No current
user-facing document presents an installed proof launcher as a normal 1.0
workflow: RFC-0075's four names are marked retired and historical.

One documentation-only clarification is warranted before 1.0: the command
reference calls the root an “ordinary ten-command” surface in its historical
and specialized section even though its current command map correctly lists
fourteen. That same paragraph groups retained diagnostics/history with
historical proof commands, which can blur the accepted distinction. A small
future documentation PR can state “fourteen-command” and distinguish retired
proof records from retained compatibility diagnostics/history. It should not
change command behavior or imply deprecation.

## Packaging and tests

The `[project.scripts]` table is explicit, complete, and directly asserted by
`tests/test_command.py`; it also asserts the four RFC-0075 proof names are
absent. Individual command tests cover the parser and behavior of each direct
implementation. This is sufficient present packaging evidence for the above
classification. No test or packaging evidence gap was found.

## Privacy and authority

No standalone surface was found to bypass a later privacy or authority
boundary. Direct standalone equivalents delegate to the same implementation as
the ordinary root. The diagnostics have their own deliberately narrow accepted
contracts: synthetic routing explanation is non-executing, actual-request
explanation has an explicit local request boundary, and RFC-0035 history stores
only allowlisted prompt-free metadata. OpenAI compatibility remains separately
loopback-only and bounded. No provider, credential, external-service, retained
configuration, or live runtime was used for this investigation.

## Recommended next steps

Make the single documentation-only clarification identified above in a separate
small PR if the project wants the command reference to state the 1.0 boundary
more plainly. Keep the current installed scripts and help behavior unchanged.

## Explicit non-recommendations

Do not remove, rename, redirect, hide, deprecate, or dynamically register any
current launcher. Do not add `hac` history or diagnostic subcommands, alias
registries, wrappers, migration machinery, or a general deprecation policy.
Do not rewrite retained RFCs, proof results, or ROADMAP.md.

## Conclusion

The current package has a coherent 1.0 candidate shape: two ordinary root
spellings, fourteen ordinary root commands, seven retained direct compatibility
spellings, and four retained narrow diagnostic/history compatibility surfaces.
The historical proof launchers have already been explicitly retired. The only
identified work is a documentation clarification; no product-surface decision
or executable cleanup is justified by this investigation.
