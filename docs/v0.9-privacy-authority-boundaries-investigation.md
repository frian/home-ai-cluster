# v0.9 Privacy and Authority Boundaries Investigation

Status: Investigation

## Purpose

This investigation audits the current `0.9.0.dev0` implementation against its
accepted privacy and authority contracts before the 1.0 contract is frozen. It
is an architecture/contract audit, not a penetration test, and changes no
runtime behavior, RFC, test, configuration, history, provider, or filesystem
state.

The answer is **yes, with the bounded qualifications below**: an operator can
reasonably predict what each ordinary surface retains, contacts, observes, and
mutates. The implementation is local-first by default and only expands into
declared remote, provider/plugin, selected-file, or Aider process authority at
the corresponding explicit caller edge or retained authorization.

## Accepted boundaries

The material contracts are RFC-0031 through RFC-0041, RFC-0045, RFC-0058,
RFC-0059, RFC-0066, RFC-0067 through RFC-0069, RFC-0072, RFC-0074,
RFC-0077 through RFC-0085, RFC-0087 through RFC-0089, and RFC-0093 through
RFC-0096. In particular:

- ordinary native clients use the fixed loopback HAC endpoint; runtime adapters
  use their explicit local loopback runtime address; static remotes come only
  from an inline, declaration, or retained operator topology;
- all HAC-owned HTTPX constructors use `trust_env=False`, do not follow
  redirects, and retain normal HTTPS verification (RFC-0085); this excludes
  provider plugins and the Aider subprocess, which own their own contracts;
- retained configuration is a closed, private fact set (RFC-0094--0096), not a
  general configuration or secrets store; and
- prompts, answers, source content, credentials, runtime health, discovery,
  scheduling, and transient request state are not accepted retained facts.

## Authority model

An invocation has one of four authority sources:

| Source | Meaning | Examples |
| --- | --- | --- |
| Explicit | Present command, path, message, declaration, or foreground-server invocation. | `code-file --file`, `external-information --plugin`, `aider`, `--declaration`. |
| Retained | Closed fact previously written by a matching `config` mutation. | Local composition, static topology, plugin name, Chat fallback boolean. |
| Inferred within authority | Deterministic selection inside already granted bounds. | Local-first routing; one local answerability decision after fallback is authorized. |
| Absent | The operation cannot use it. | Plugin network in ordinary Chat without both retained conditions; filesystem mutation from `code`. |

No audit evidence shows a command silently persisting a CLI override, selecting
a provider merely because it is installed, or treating untrusted model/source
content as configuration or new authority.

No HAC-owned client obtains proxy or CA behavior from ambient HTTPX environment

This audit did not treat OS routing, DNS, VPN, Tailscale, or an external
provider/subprocess implementation as HAC-owned proxy behavior.

## Retained configuration

`hac config show` loads and formats only the validated private document. It
does not construct a runtime, probe a runtime or remote, resolve/import a
plugin, read provider credentials, perform DNS/HTTP, or start a lifecycle
action. Reading retained configuration elsewhere likewise parses facts only;
startup consumption does not rewrite, normalize, or persist them.

The mutations remain separated. `config external-information --plugin NAME`
changes only the selected plugin; it does not authorize Chat fallback. `config
chat --external-information-fallback` changes only the boolean; it does not
choose or import a plugin. Local and node mutations preserve the other closed
domains. Inline topology and `--runtime-config` are invocation-local and do
not rewrite retained state. Remote topology describes a remote; it does not
configure that machine.

This is a D assessment. The only deliberate display of topology/model facts is
the explicitly requested `config show` result; it does not display a credential
because the schema cannot contain one.

## External information and Chat fallback

`hac external-information` requires a query, a question, and either its one
invocation `--plugin` or a retained plugin selection. It discovers and loads
only the exact selected entry point, invokes it once, validates one to five
closed source candidates, then makes one source-grounded loopback Chat request.
Plugin load/acquisition failure is terminal and never chooses another plugin or
silently changes disclosure authority.

One-shot native `hac chat MESSAGE` remains normal native/local-cluster Chat
unless all of the following are true: the operator retained the fallback
boolean, retained a plugin name, and supplied an eligible (at most 4,096-byte)
message. Only then may HAC ask the fixed local decision endpoint with the exact
question. An `external` decision permits exactly one acquisition through that
retained plugin and exactly one source-grounded request; an acquisition failure
terminates. A decision does not grant configuration/provider authority itself.

Interactive Chat deliberately does not consume this fallback. Its bounded
conversation is process-local and native-only, as RFC-0087/RFC-0096 require.
Provider credentials remain plugin/provider-owned and are neither retained nor
displayed by HAC core. This is D.

## Code and filesystem authority

`hac code` sends bounded text to the ordinary native `code` capability. It
does not execute generated text, launch tools, select files, or write state;
interactive mode only retains its bounded conversation in the foreground
process. This is D.

`hac code-file` reads one selected non-symlink UTF-8 target (or validates one
missing leaf with an existing parent), omits the path from the model request,
validates one closed content-only result, and atomically replaces only that
target. No parent/sibling/model-selected path, retry, execution, or general
filesystem authority is present. Existing symlinks and non-regular files fail
closed. The explicit RFC-0081 empty-leaf behavior above is covered by focused
tests. This is D.

`hac aider` is intentionally broader, explicit caller-edge process authority.
It validates one target, may create one exact missing target under RFC-0069,
starts one private loopback translator, and invokes the supported Aider child
with a fixed privacy/fail-closed argument set. The child receives the inherited
environment except the confirmation override; its own credentials/network are
subprocess-owned, not HAC-owned. HAC does not capture child prompt/result
history, and its temporary Aider files are process-lifetime only. This is D,
not a reason to call explicit Aider authority a core privacy defect.

## Browser and loopback authority

`local` defaults to `127.0.0.1:25042` and accepts an explicit `--host` override;
its browser page is attached only at the default loopback host. `static-cluster`
is fixed to `127.0.0.1:25042`, while `compatibility` is fixed to
`127.0.0.1:8001`. Static-cluster remote reachability is outbound to explicitly
declared topology and does not expand its fixed loopback listening interface.

The browser uses same-origin requests, local vendored PDF.js with supplied
bytes, and `textContent` output rendering. Its only `localStorage` key is the
accepted theme preference. Chat/Code arrays, attribution, form input, results,
and local file/PDF extraction are page memory only. This is D.

## Request history

The only writer is the retained specialized command
`home-ai-cluster-explain-request --record-history`. It explicitly performs its
own request/account operation, then retains only `status`, requested capability,
selected candidate family, outcome rule, and failure status. Ordinary Chat,
Code, Code File, Aider, summarize, classify, external-information, and browser
requests do not opt into history. `home-ai-cluster-history` reads local state
only; `home-ai-cluster-clear-history` unlinks only HAC's history path; neither
has network authority. This is D.

## Read-only and observational commands

`preflight` reads an optional declaration and static adapter/node metadata only;
focused tests make health, capability, and request calls fail if attempted.
`config show` is local read-only as described above. `home-ai-cluster-explain-routing`
uses a synthetic non-executable adapter and performs no request. These have no
runtime/remote observation or mutation authority.

`health` is different by contract: it directly probes the configured local
runtime once and reports its observation. `status` performs one local runtime
observation and one bounded status request per declared remote. Neither is
hidden activity because each command's purpose and documentation explicitly
state it. `local`, `static-cluster`, and `compatibility` are foreground servers,
not static/read-only commands; construction has no probe, while later client
traffic uses their declared composition. All are D.

## Error and output privacy

The completed diagnostics investigation already establishes the bounded native
failure vocabulary. This audit found no additional ordinary failure path that
prints a prompt, response, acquired source content, credential/API key,
authorization header, raw retained JSON, HTTPX/Pydantic detail, subprocess
command line, or traceback. Successful `--json`/`--verbose` output may
intentionally include the selected result, attribution, and for source-grounded
Chat the supplied evidence; that is the requested operation result, not hidden
retention or failure leakage. This is D.

## Documentation and test coverage

README, Getting Started, command reference, and canonical operator workflow
agree on `hac` as the ordinary surface; the command reference describes the
configuration separation, explicit external-information selection, Code File,
Aider, loopback defaults, and observational commands. No false privacy or
authority claim was found.

Focused tests cover retained-schema closure and private file modes, config
mutation separation, startup precedence/no rewrite, HTTPX environment
isolation, exact plugin selection, one-shot fallback and interactive exclusion,
history allowlisting, Code non-execution bounds, Code File symlink/atomic/empty
leaf behavior, Aider privacy arguments, loopback theme storage, preflight's
non-observation, and safe errors.

## Findings

1. **Priority 8 — C: `config show` non-observation proof is indirect.** The
   implementation is plainly a parse/format path and tests lock its output,
   but no focused sentinel test currently makes HTTP, plugin entry-point
   discovery/import, credential lookup, and adapter construction fail while
   exercising `config show`. Add one focused test when changing config code;
   no implementation change is warranted.
2. **Priority 8 — C: browser persistence proof is structural rather than a
   browser-runtime refresh test.** Tests tightly assert the sole storage key
   and page code, but a small browser harness could demonstrate that refresh
   retains only theme and discards Chat/Code content. No behavior defect was
   found.
3. **Priority 8 — C: ordinary request paths have strong negative evidence but
   no single cross-command history-writer inventory test.** `record_account`
   has one production caller and focused history tests prove its allowlist;
   add a narrow import/call-site inventory or command-level regression test if
   that uniqueness becomes a frozen 1.0 proof requirement.

All material behavioral findings are D. There are no A findings (no accepted
contract violation), and no B findings (no unresolved authority decision).

## Recommended next steps

If additional 1.0 evidence is desired, make one tests-only follow-up that adds
the three small C proofs above. Do not combine it with a security framework,
configuration redesign, provider abstraction, browser redesign, proxy policy,
or runtime behavior change.

## Explicit non-recommendations

Do not add authentication, authorization frameworks, secret managers, encrypted
configuration, databases, telemetry, audit logs, policy engines, sandboxes,
firewalls, Docker/Kubernetes, generic plugin/provider machinery, automatic
retrieval, provider fallback, prompt/result logging, or a Code execution
surface. Do not reinterpret explicit selected-file or Aider authority as an
unaccepted defect.

## Conclusion

The current 0.9 ordinary and retained compatibility surfaces have predictable,
explicit authority boundaries suitable for the 1.0 candidate contract. HAC
does not retain prompts, responses, acquired content, or credentials; it does
not exercise hidden external network authority; and it does not mutate beyond
the explicitly selected configuration, history, Code File, or Aider scope.
The remaining work is narrowly targeted proof consolidation, not behavioral
hardening or a new architectural decision.
