# v0.9 Retained Configuration Hardening Investigation

Status: Investigation

## Purpose

This investigation audits the implemented retained-configuration surface before
the `1.0` contract is frozen. It makes no implementation or RFC decision.
The investigation uses the accepted contracts in RFC-0094, RFC-0095, and
RFC-0096 as its architectural baseline; observations below describe current
`main` at `440bd64`.

## Current accepted contract

RFC-0094 makes retained configuration an optional, HAC-managed local baseline,
not a public editable-file API. It separates local runtime composition and
caller-local routing capabilities from caller-owned retained remote topology.
`hac config show` reports retained facts only and performs no runtime or
cluster observation. Explicit compatible CLI values are one-invocation,
non-mutating overrides; an explicit different runtime replaces the runtime
domain, while `--runtime-config`, an explicit declaration, and complete inline
topology are self-contained alternatives.

RFC-0095 adds one separate optional retained exact acquisition-plugin choice.
It grants no execution authority without an explicit external-information
operation. RFC-0096 adds a distinct retained Chat-fallback authorization; it
is neither a plugin choice nor general network authority. Neither RFC makes
credentials, prompts, responses, provider configuration, discovery, health, or
runtime observation retained facts.

RFC-0094 further requires malformed retained state to fail locally and visibly,
and requires retained local and remote configuration to be operator-correctable
and removable. Its physical location and serialized representation remain
private implementation details.

## Current implementation shape

`retained_configuration.py` owns a closed JSON document, validation, and
persistence. It stores four top-level facts: local composition/caller-local
capabilities, ordered remote nodes, optional external-information plugin, and
Chat fallback authorization. Loading accepts a missing file as empty state,
but requires an exact top-level key set and exact nested key sets. Validation
rejects malformed JSON or UTF-8, structural variation, invalid compositions,
invalid capabilities, invalid plugin names, non-boolean Chat authorization,
duplicate node IDs, and duplicate normalized remote URLs.

Saving serializes a validated complete document, creates a new application
directory with mode `0700`, writes a same-directory temporary file with mode
`0600`, then uses `os.replace`; the cleanup path removes a remaining temporary
file after a replacement failure. Existing application-directory permissions
are deliberately not changed. The implementation and focused tests establish
atomic replacement and owner-only file mode, but do not claim crash-durability
(`fsync`) semantics.

All five mutating `hac config` forms load the complete retained document before
building and saving a replacement document. Local and static-cluster startup
load it only when the relevant retained domain is applicable. `--runtime-config`
bypasses retained runtime loading; a declaration or complete inline topology
bypasses retained topology loading. `config show` only loads and formats it.

## Audit method

Code and focused tests were inspected for the command surface, parser and
startup consumption, validation, persistence, privacy handling, and current
operator documentation. Isolated commands used a fresh temporary
`XDG_CONFIG_HOME`; no runtime was started and no network operation was
performed.

The isolated lifecycle confirmed empty `show`; first local configuration;
node add, in-place update, and ordered multiple nodes; plugin and Chat
authorization set; complete `show`; local reset; node removal; plugin reset;
and Chat reset. Each successful mutation printed its short success line to
stdout with exit `0`; invalid argument combinations use argparse stderr and
exit `2`; retained-load and save failures use a bounded `error: ...` stderr
message and exit `1`. `show` with no facts prints each domain as not configured,
none, or not authorized. It prints all configured local, ordered node, plugin,
and authorization facts when present.

Invalid UTF-8, malformed JSON, wrong top-level type, missing or unknown
top-level fields, malformed local/remote facts, duplicate IDs or normalized
URLs, invalid capabilities or plugin names, and a non-boolean Chat flag all
fail before startup or mutation. Existing tests also show errors omit private
paths and raw serialized content. A practical unreadable-file case is mapped
to the bounded `unable to read retained configuration` error by the `OSError`
handler; it is not treated as absent state.

## Findings

### 1. Invalid retained state cannot be recovered through `hac config` (A)

**Reproduced observation.** With an isolated malformed document containing
only `{"local": null}`, each of the following exited `1` with
`error: invalid retained configuration shape` before mutation:

```text
hac config show
hac config local --reset
hac config node missing --remove
hac config external-information --reset
hac config chat --reset
```

The same load-before-mutate structure also blocks local replacement, node
addition/update, plugin setting, and Chat authorization setting. The existing
commands can correct valid state and preserve unrelated domains, but offer no
supported recovery path when the document cannot be loaded.

This is a concrete RFC-0094 contract-hardening gap: its explicit
operator-correctable/removable requirement already authorizes a small recovery
correction. It does not authorize a general editor, migration framework, or
new configuration architecture. A follow-up should first choose the smallest
behavior that permits safe removal/correction without trusting invalid values,
and prove it for malformed, structurally incompatible, and unreadable cases.

### 2. Additive private fields strand valid prior retained state (A)

**Reproduced observation.** Current loading rejected both representative
previously valid private documents:

```text
RFC-0094-era: local + remote_nodes                         -> exit 1
post-RFC-0095/pre-RFC-0096: plus external_information_plugin -> exit 1
current four-field representation                          -> exit 0
```

The exact-key parser treats omitted later optional fields as an invalid shape.
Consequently, an ordinary upgrade can strand an otherwise valid retained local
composition and topology before any startup, `show`, or supported mutation.

This is an already-authorized compatibility correction, not a request to make
the private JSON schema public or to add schema versions. RFC-0095 calls the
plugin fact optional; RFC-0096 explicitly gives an absent authorization the
meaning `false`; RFC-0094 requires retained state to remain a usable baseline.
A minimal backward-compatible default for absent later optional facts preserves
those accepted meanings. Any broader interpretation of unknown fields,
arbitrary shape changes, or durable migration policy would require an RFC.

### 3. Recovery and additive-loading cases lack focused product tests (C)

Current tests strongly cover valid lifecycle, structural rejection,
privacy-safe errors, persistence mechanics, and startup override semantics.
They do not test supported-command recovery from an unloadable document or
loading the two representative prior documents. Add focused tests with any
already-authorized correction. Documentation should state only recovery that
is actually available; current operator reference documents the commands but
does not claim a malformed private document is recoverable.

### 4. Normal lifecycle, domain preservation, and ergonomics are bounded (D)

For valid state, `local --reset` preserves nodes, plugin choice, and Chat
authorization; node removal preserves local and other nodes; plugin and Chat
resets preserve all other domains. Node upsert replaces its complete
declaration without changing its order; new nodes append. `node --remove`
reports a missing node on stderr and exits `1`; reset is idempotent. Mutation
does not require unrelated values to be re-entered. The wording distinguishes
retained inspection from health/status/preflight, and `show` is intentionally
human-readable rather than a serialized-file API.

## Upgrade compatibility

The private representation has changed additively twice, but current exact-key
loading is not additive. The two reproduced prior forms therefore fail safely
and privately, but not compatibly. Silent acceptance of unknown fields would
be a separate compatibility decision and is not recommended here. The narrow
safe behavior already implied by the accepted RFCs is only defaulting absent
later optional facts while retaining validation of all accepted facts.

## Recovery behavior

Malformed or structurally incompatible retained state is **not recoverable
through the supported current `hac config` surface**. `show` and every reset,
remove, set, add, or update operation load the complete document first. The
implementation does correctly fail locally, visibly, without network activity,
automatic rewrite, or leakage of raw contents and private paths, but it misses
the separately required correctable/removable product property.

The product must also decide and document the bounded behavior for a genuinely
unreadable file before calling recovery complete. This is a concrete edge of
the existing RFC-0094 recovery requirement, not authority to introduce a
general repair system.

## Privacy and authority review

No inspected retained-state load, show, or configuration mutation observes a
runtime, resolves DNS, contacts a node/provider, discovers/imports a plugin,
or reads provider credentials. Startup consumption is local parsing and
validation; runtime and remote observations remain in their explicit health or
status paths. Retaining a plugin alone remains inert. Chat fallback remains
separate from plugin selection and only its accepted caller path may disclose
an eligible question.

The retained model names and remote URLs are displayed only by explicit
`config show`; normal retained-state errors are category-level messages. No
prompts, generated responses, acquired source content, or credentials are
serialized by this module. These are no-issue areas for this investigation.

## Documentation and test gaps

The command reference correctly describes retained state as an optional
baseline, temporary overrides, reset/remove behavior, no observation in
`show`, the private-file boundary, plugin selection versus authority, and
separate Chat authorization. It should not be strengthened to promise malformed
state recovery until that behavior exists. After a correction, document the
exact supported operator action and its limits, rather than suggesting manual
editing of the private file.

Focused tests should cover: each supported recovery action from corrupt state;
whether an unreadable document has a supported recovery route; RFC-0094-era
loading; RFC-0095-era loading; non-mutation while defaulting older documents;
and all expected privacy-safe error forms. Existing persistence tests already
cover directory creation, mode `0600` files, same-directory temporary files,
replacement, and temporary cleanup.

## Classification

| Finding | Classification | Basis |
| --- | --- | --- |
| Invalid state blocks every supported correction action | A | RFC-0094 already requires operator-correctable and removable retained state. |
| Omitted later optional fields reject prior valid state | A | RFC-0094 baseline compatibility plus RFC-0095 optionality and RFC-0096 absent=`false` authorize narrow defaulting. |
| No focused recovery/prior-document coverage | C | Tests/documentation need to prove any accepted correction; no new architecture is needed. |
| Valid-state lifecycle, overrides, privacy, authority, and persistence shape | D | Current implementation, tests, and isolated lifecycle evidence are sufficiently bounded. |

No Category B decision is required for the two smallest corrective gaps. A
Category B RFC would be required before accepting unknown fields, versioned
schemas, general migration, manual-edit support, profile/inheritance behavior,
or any new configuration domain.

## Recommended next steps

1. Make one small implementation PR for RFC-0094 recovery and the two
   already-implied additive defaults, with focused tests and no new command or
   generalized migration layer.
2. Update operator documentation in that PR only to describe the recovery
   behavior actually implemented.
3. If a proposed fix needs unknown-field compatibility, a version marker,
   rewriting an untrusted document, or recovery semantics beyond removing or
   correcting retained state, stop for an RFC first.

## Explicit non-recommendations

This investigation does not recommend profiles, inheritance, import/export,
named environments, synchronization, secrets management, provider-option
frameworks, configuration databases, dynamic discovery, runtime inventory,
capacity/scheduling, dashboards, Docker, Kubernetes, or a generic
configuration abstraction. It does not recommend a public retained-file schema
or manual-file-edit workflow.

## Conclusion

The valid retained-configuration product surface is small, private,
non-observing, and consistent with accepted local-first and authority
boundaries. Before `1.0`, it needs two bounded hardenings already authorized by
accepted RFCs: a real supported recovery path for unloadable retained state and
backward-compatible loading of documents that predate additive optional facts.
