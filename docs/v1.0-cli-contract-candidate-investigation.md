# Home AI Cluster 1.0 CLI Contract Candidate Investigation

Status: Investigation

## Purpose

This is an investigation-only inventory of the current `0.9.0.dev0` command
line surface.  It does not create a 1.0 specification or compatibility policy,
and does not authorize a command, option, output, packaging, or architecture
change.  Its question is narrower: which user-visible contracts are mature
enough to take into fresh-install two-node operator validation as the 1.0
candidate, and what still needs a deliberate compatibility decision or proof?

“Candidate stable” below means an accepted, implemented, documented, and
focused-tested product behaviour that 1.0.x should normally preserve.  It does
not mean that every current parser implementation detail, help line, byte
limit, JSON serialization detail, or third-party diagnostic is frozen.

## Accepted foundations

This audit uses the current Vision, Foundations, Principles, Non-goals, release
direction, operator documentation, and RFC index as authority.  The material
accepted decisions include the ordinary root (RFC-0050 and RFC-0052), static
topology/routing and inspection (RFC-0036 through RFC-0044 and RFC-0058/
RFC-0059), finite requests and outputs (RFC-0045, RFC-0048 through RFC-0049,
RFC-0051 through RFC-0057, RFC-0060 through RFC-0061, and RFC-0067), bounded
caller edges (RFC-0068 through RFC-0069, RFC-0072, RFC-0080 through RFC-0081),
runtime composition (RFC-0071, RFC-0073 through RFC-0074, RFC-0089 through
RFC-0090), interactive Chat/Code (RFC-0087 through RFC-0088), the short-option
vocabulary (RFC-0092), retained configuration (RFC-0094 through RFC-0096),
and the separately installed external-information boundary (RFC-0077 through
RFC-0079 and RFC-0091/RFC-0093).

The release direction requires a predictable 0.9 candidate, not a feature
freeze of incidental details.  The persistent conclusions of the v0.9
configuration, diagnostic, legacy-surface, and privacy/authority investigations
are used as evidence and are not reopened here.

## Option and default boundaries

This is the compact public invocation inventory.  Long forms are the ordinary,
supported spellings.  The finite short vocabulary (`-h`, `-f`, `-d`, `-l`,
`-j`, and existing `-v` where available) is accepted by RFC-0092 and is a
candidate stable equivalent spelling, not merely argparse trivia.

| Area | Candidate-stable option/input contract | Flexible/private boundary |
| --- | --- | --- |
| Runtime | `--runtime {ollama,llama-server}`; Ollama `--ollama-model`, `--ollama-disable-thinking`; llama-server `--llama-server-base-url` and `--llama-server-model`; closed `--runtime-config PATH` alternative | Adapter classes, HTTP helpers, TOML parsing implementation, and new adapter additions. |
| Local bind | `local --host`, `--port`; ordinary default is loopback `127.0.0.1:25042` and browser availability is only for that exact host | Other host/browser presentation and Uvicorn diagnostics; do not promise markup or server formatting. |
| Static topology | `-d/--declaration`; or complete inline `--remote-node-id`, `--remote-base-url`, repeated `--remote-capability`, and repeated `--local-capability` | TOML whitespace/order/serialization mechanics; declaration is an operator-owned input contract, not a generic configuration framework. |
| Finite requests | Positional-or-`--message` where documented; `--text`/`--file`/stdin source selection; repeated labels; `--timeout-seconds`; `--verbose`; `--json` | Defensive numeric bounds unless an accepted RFC makes the specific bound semantic; human prose layout. |
| External information | `--plugin`, positional QUERY QUESTION or `--query`/`--question`; retained plugin may supply the selection | Provider-specific plugin options, provider names/credentials, discovery internals, provider network behaviour. |
| Code File/Aider | One `--file` target and one message; intentional selected-leaf creation limits | Temporary files, private translator address, child-process arguments, and Aider internals. |
| Config | `local`, `node`, `external-information`, `chat`, `reset`, `show`, including targeted `--reset`/`--remove` forms | Physical path, JSON representation, temp-file details, and private validation helpers. |

Candidate stable defaults are the local-first routing rule; ordinary fixed
loopback host/port; default Ollama composition and its existing `llama3.2`
model; ordinary local capability availability; `chat, summarize` compatibility
defaults when static caller/local or remote capability sets are omitted; the
120-second native-client timeout; foreground interaction when a supported
no-message command has TTY stdin and stdout; human-readable default output;
and JSON/verbose only when explicitly requested.  Missing retained state is an
empty baseline, not an error.  The fixed static-cluster and compatibility
loopback boundaries are architectural; exact implementation bind calls are not.

## Retained configuration contract

`config local`, `config node`, `config external-information`, `config chat`,
`config reset`, and `config show` are candidate-stable exact subcommands.
`local` is a complete local composition/caller-local capability replacement;
`node` adds or replaces one ID while retaining other declared order; targeted
reset/remove preserves unrelated facts; and whole `config reset` is the
explicit recovery path that can remove malformed retained state without first
loading it.  `show` is local and read-only: it does not probe runtime, nodes,
plugins, DNS, HTTP, or mutate state.

Explicit compatible CLI values are one-invocation, non-mutating overrides.
An explicit different runtime replaces the runtime domain; an explicit runtime
composition file, declaration, or complete inline topology is self-contained.
Invalid retained state fails closed with bounded local diagnostics on normal
use, rather than being silently ignored.  The config file’s location, on-disk
JSON/schema, permissions mechanics, temporary name, and serialized field order
are private implementation details and must not become a manually edited 1.0
file-format promise.

## Capability, runtime, and static-cluster contract

The accepted ordinary capability names are `chat`, `summarize`, `classify`, and
`code`; their meanings and explicit admission are candidate stable.  Routing is
capability-centered, local-first, deterministic within caller-owned topology,
and uses declared remote order as the sole remote priority.  Capability order
is not priority; declarations control eligibility, not live receiver truth,
runtime health, model selection, scheduling, discovery, load balancing, or
runtime lifecycle.  Adding a new accepted capability appears architecturally
additive, but whether that is automatically compatible for every script is an
unresolved product question below.

`ollama` and `llama-server`, their selection options, and their process-local
adapter-specific settings are candidate stable.  The durable promise is that
ordinary HAC requests remain capability-centered and adapters remain
replaceable; it does not promise a closed forever adapter set.  A new adapter
behind that boundary is plausibly additive, subject to ordinary product review.

Static operation remains explicit: no dynamic discovery, registration,
scheduler, load balancer, remote lifecycle ownership, or remote capability
advertisement.  Declaration and complete inline modes are alternative
per-invocation topology sources; retained topology is the optional baseline.
`preflight`, `health`, and `status` intentionally differ: respectively static
coherence/no network, local runtime observation, and local-plus-declared-remote
observation.  That distinction is candidate stable.

## Finite, interactive, external-information, and Aider boundaries

One-shot Chat, Code, Summarize, and Classify input shapes are candidate stable.
Chat and Code no-message interactions are TTY-only, process-owned, non-
persistent conversations; successful turns retain ordered in-process context,
failed turns roll back, and EOF/Ctrl-C ends the session.  Interactive Chat has
no external-information fallback.  Exact prompts and progress glyphs are not
the contract; content on stdout, progress/recoverable diagnostics on stderr,
and the non-persistence/rollback boundary are.

Code remains textual and non-executing.  Code File has one explicitly selected
file authority, validates then atomically replaces it, and does not turn Code
into generic filesystem authority.  Aider is one explicit subprocess/tool
edge: HAC owns only its bounded translation and selected-target guardrail;
Aider’s upstream interface, private translator machinery, and temporary files
are outside HAC’s compatibility promise.

External information is not HAC-core provider compatibility.  An explicit
operation, or separately retained Chat fallback authorization, can select one
separately installed plugin, make at most one bounded acquisition, validate
source evidence, then make one source-grounded Chat request.  Plugin choice is
separate from Chat disclosure authority.  No installation-only, startup,
ordinary Chat, interactive Chat, provider fallback, query rewrite, URL
following, or hidden acquisition authority is promised.

## Output, exit-code, and machine-readable boundaries

For finite commands, default human-readable success plus documented JSON and
verbose availability are candidate stable.  Chat, Code, Summarize, Classify,
and external-information retain content/result stdout; verbose adds attribution;
successful Code File remains silent.  Inspection commands are human-readable by
default and support JSON.  Field ordering and whitespace are not stable.

The candidate exit contract is: help/version/success exit 0; accepted parser or
input misuse exits 2; bounded finite operational failure exits 1; a completed
incoherent preflight report exits 1; and completed negative health/status
observations exit 0.  Bounded HAC diagnostics belong on stderr without raw
tracebacks, request content, credentials, or private details.  After HAC
constructs a foreground application, Uvicorn/OS lifecycle diagnostics and
their exact non-zero values remain third-party/OS-owned.

JSON availability is candidate stable where documented.  Current result field
names have strong implementation and focused-test evidence, but accepted
material does not state an exact versioned JSON schema or a general additive-
field policy.  Therefore exact per-command JSON field schemas remain unresolved
for the final 1.0 promise: scripts may rely on documented semantic output
and current examples during candidate validation, but this investigation does
not silently promise every current key/value shape.  Ordering is irrelevant;
whether optional additive fields are compatible needs a small explicit product
decision before final compatibility language.

## Stability boundary and additive evolution

| Contract area | Candidate stable | Intentionally flexible/private | Unresolved |
| --- | --- | --- | --- |
| Roots/commands/options | Exact accepted roots, command names, documented invocation shapes and accepted short forms | Help prose/order, argparse internals | Whether a new ordinary root command is automatically compatible in 1.x |
| Defaults/semantics | Local-first, fixed ordinary/compatibility/static loopback boundaries, explicit authority, routing and inspection semantics | Cosmetic/default presentation values not accepted as architectural | Which defensive limits deserve final public-compatibility status |
| Output/errors | Channels, exit classes, bounded privacy-safe categories, JSON availability | Whitespace, human wording, third-party diagnostics | Exact JSON fields and additive JSON-field rule |
| Retained config | CLI facts, override precedence, reset/recovery, read-only show | File path/serialization/temp details | None found |
| Engines/plugins/capabilities | Engine-independent boundary; currently accepted names and semantics | Classes, provider configuration/credentials, separately packaged provider details | Compatibility effect of adding a capability/plugin/runtime |
| Launchers | Current retained compatibility names and roles | Help cosmetics, internal entry points | Duration/conditions of 1.x retention beyond the initial candidate |

Adding a non-conflicting optional flag, runtime adapter, separately packaged
plugin, or optional JSON field is likely compatible only when it does not alter
existing invocation, authority, output, or routing semantics.  A new ordinary
command has a larger namespace/documentation implication and is not declared
automatically compatible here.  These are compatibility assessments, not a new
semantic-versioning policy.

## Unresolved compatibility questions

1. **Exact JSON schemas and additive fields (product decision).** Decide
   whether any documented result fields are a final machine-readable promise,
   and whether additive optional fields are compatible.  This is a small
   documentation/product decision unless it changes architecture.
2. **Future ordinary root commands (product decision).** Decide whether an
   added command in 1.x is compatible by default.  No RFC is presently needed
   unless the decision changes the command-namespace architecture.
3. **Future capability additions (product decision).** RFC-0066 supplies
   admission semantics, but does not itself settle compatibility expectations
   for scripts that assume today’s closed set.
4. **Compatibility-launcher retention horizon (RFC/product decision).** The
   present package should keep them through the 1.0 candidate.  A blanket
   all-1.x removal/retention policy is not explicitly accepted; removal or
   promotion would require an explicit decision, normally an RFC.
5. **Exact bounded numeric limits (product decision).** Retain limits whose
   RFC purpose is semantic safety; do not freeze every defensive parser limit
   without accepted evidence.

## Two-node operator validation handoff

| Candidate contract | Why real validation matters | Operator test action |

| Retained local/runtime and remote topology configuration | Requires real per-machine state and restart | Configure local runtime and ordered remote topology; use `config show`; restart and confirm retained facts are applied. |

Do not run this two-machine exercise in this investigation PR.  It must choose
its real hardware, runtime, and model from supported documentation rather than
claiming this report makes one canonical.

## Recommended next steps

The ordinary CLI is defined precisely enough to enter final operator validation
as the 1.0 candidate.  Before making the final 1.0 compatibility promise,
resolve the small B compatibility-language questions—first and most importantly
JSON schemas/additive fields—and perform the bounded fresh-install two-node
checklist.  A focused documentation/test proof follow-up may then consolidate
the adopted answer; no CLI/runtime/architecture change is indicated.

## Explicit non-promises

This investigation does not freeze help prose, whitespace, cosmetic ordering,
private retained-config representation/path, implementation classes/modules,
internal HTTP helpers, temporary files, tests, browser markup/style, provider
details, or third-party Uvicorn/Aider diagnostics.  It does not promise that
new runtimes/plugins/capabilities can never be added, and it does not create
version negotiation, aliases, registries, migration machinery, or a generic
compatibility framework.

## Conclusion

The ordinary surface is a credible 1.0 candidate: both roots, all fourteen
ordinary names and their accepted invocation/authority/routing semantics, the
retained configuration boundary, and retained compatibility launchers are
sufficiently bounded.  It is ready for final operator validation, not yet a
final compatibility promise.  The remaining decisions are narrow and explicit
rather than evidence of a product-contract defect.
