# Home AI Cluster 1.0 Five-Node Validation

Status: Evidence record

Date: 2026-09-04

This document records a factual manual validation of the published Home AI
Cluster `1.0.0` release. Its purpose was to exercise a larger explicit static
cluster. It records already released behavior; it introduces no feature or
architectural change. The testing rule was:

> Observe. Reproduce. Record. Fix only real bugs.

## Test topology

The caller/orchestrator was `rasp`, running HAC `1.0.0` with Ollama and local
model `llama3.2:1b`. It declared the caller-local `classify` capability and
ran the ordinary static-cluster caller/orchestrator.

The explicit remote nodes below are retained in declaration order. The Debian
nodes were exposed through explicit Incus host proxy ports.

| Node | Base URL | Capability | Runtime | Model | Notes |
| --- | --- | --- | --- | --- | --- |
| `sat` | `http://192.168.1.9:25042` | `code` | Ollama | `qwen2.5-coder:7b` | — |
| `debian-1` | `http://192.168.1.9:25043` | `chat` | Ollama | `llama3.2:1b` | Incus container |
| `debian-2` | `http://192.168.1.9:25044` | `summarize` | Ollama | `llama3.2:1b` | Incus container |
| `debian-3` | `http://192.168.1.9:25045` | `code` | Ollama | `llama3.2:1b` | Incus container |

## Validation scenarios and observed results

### 1. Baseline capability routing

The baseline routing results were:

| Capability | Execution location |
| --- | --- |
| `classify` | `rasp` / local |
| `code` | `sat` |
| `chat` | `debian-1` |
| `summarize` | `debian-2` |

Successful results correctly reported their execution attribution.

### 2. Duplicate `code` capability and static precedence

Both `sat` and `debian-3` declared `code`. With both reachable, a `code`
request executed with:

```text
node_id = "sat"
model = "qwen2.5-coder:7b"
```

This demonstrates the released deterministic retained-order behavior. It is
not load balancing.

### 3. Safe fallback to the second `code` remote

With the `sat` receiver unavailable before request transmission, `sat` could
not be used. Nodes without `code` were not selected, and HAC continued to
`debian-3`, where the request completed successfully with:

```text
node_id = "debian-3"
model = "llama3.2:1b"
```

A reproduced fallback request completed in approximately 9.6 seconds. This is
the released safe pre-transmission fallback behavior; it does not establish
execution-availability awareness.

### 4. Static precedence restored after recovery

After restoring the `sat` receiver, the next `code` request returned to `sat`
without caller reconfiguration. This confirms deterministic static precedence
restoration after recovery.

### 5. `chat` node failure and capability isolation

Baseline `chat` completed on `debian-1`. After `debian-1` was stopped, the
connection to `192.168.1.9:25043` was refused. The only eligible `chat` remote
was therefore unavailable before transmission, and the CLI returned:

```text
error: runtime adapter unavailable
exit=1
```

This is the released 1.0 mapping for this exhausted remote-capability path.
While `debian-1` was unavailable, `code` continued successfully on `sat` and
`summarize` on `debian-2`. After restarting `debian-1` and its HAC receiver,
`chat` again completed on `debian-1` without caller reconfiguration. This
demonstrates capability isolation and recovery.

### 6. `summarize` node failure and capability isolation

Baseline `summarize` completed on `debian-2`. After `debian-2` was stopped,
the connection to `192.168.1.9:25044` was refused and the CLI returned:

```text
error: runtime adapter unavailable
exit=1
```

While `debian-2` was unavailable, `chat` continued successfully on
`debian-1` and `code` on `sat`. After restarting `debian-2` and its HAC
receiver, `summarize` again completed on `debian-2` without caller
reconfiguration. This demonstrates capability isolation and recovery.

### 7. Caller/orchestrator restart and retained configuration

Before restart, retained configuration contained local `classify`; `sat` for
`code`; `debian-1` for `chat`; `debian-2` for `summarize`; and `debian-3` for
`code`. `hac static-cluster` was stopped on `rasp`. While stopped, local port
`25042` was no longer listening and an ordinary CLI request returned:

```text
error: ordinary cluster unavailable
exit=1
```

`hac static-cluster` was restarted without any `hac config` command. The
retained topology remained intact, and post-restart routing was revalidated:

| Capability | Execution location |
| --- | --- |
| `classify` | local |
| `chat` | `debian-1` |
| `code` | `sat` |
| `summarize` | `debian-2` |

This demonstrates that retained configuration is sufficient to reconstruct the
ordinary explicit static cluster after caller/orchestrator restart.

## Non-reproducible transient observation

During one fallback attempt to `debian-3`, an ordinary request exceeded the
180-second HAC timeout. Follow-up investigation found Ollama itself running
normally, direct `llama3.2:1b` inference completing in approximately 27
seconds, and the same HAC fallback path reproducing successfully immediately
afterward. A subsequent HAC request completed on `debian-3` in approximately
9.6 seconds.

This is classified only as a **Non-reproducible transient observation**. It is
not called a bug, no cause is asserted, and no fix is implied.

## Conclusions

For the published 1.0 behavior, this validation establishes explicit static
node membership; capability-based routing; duplicate capability declarations;
deterministic candidate precedence; capability filtering; safe
pre-transmission fallback; targeted node failure; capability isolation;
recovery without reconfiguration; restoration of static precedence; retained
configuration across caller/orchestrator restart; and execution attribution.

## What this validation does not establish

This validation does not establish load balancing, generic scheduling,
execution availability, runtime-capacity awareness, configurable slots,
fairness, dynamic discovery, dynamic membership, shared distributed state, or
failover after an ambiguous or post-transmission failure.
