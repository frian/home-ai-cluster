# O-08 Retained Inspection Semantics Investigation

Status: Investigation record

## 1. Scope

This is a documentation-only investigation of O-08 from the real 1.0 two-node
operator validation: retained HAC configuration is shown by `hac config show`
and used by zero-argument `hac static-cluster`, while zero-argument
`hac preflight` remains local-only and `hac status` requires an explicit
declaration. It makes no CLI, retained-configuration, preflight, status,
routing, runtime, network-authority, test, or RFC change.

The investigation started from clean `main` at
`4e9707091b116f357c91b0228a945c452479efe0` (the expected merge commit after
PR #622). Reproduction used a disposable `XDG_CONFIG_HOME` and `HOME`, with
only `documentation-model`, `summary-remote`, and `127.0.0.1:25042`; no real
operator configuration, address, runtime, or remote machine was used.

## 2. Real operator observation

The observed retained state was an Ollama local composition, caller-local
`chat`, and a `summary-remote` eligible for `summarize`. `hac config show`
reported those retained facts. Bare `hac static-cluster` used them, so Chat was
locally eligible and Summarize remotely eligible. In contrast, bare preflight
reported the historical ordinary local registry, and bare status was rejected
before any observation because `-d/--declaration` is required.

The distinction is not evidence that the latter two are defects. These are
different operator questions and, crucially, status has network authority.

## 3. Accepted contracts

RFC-0036 deliberately made the first preflight local-only, read-only and
network-free. Its stable result identifies `operating_mode: local-only`; it
does not activate distributed paths. Its small result shape and output/exit
behaviour are compatibility obligations. Later RFC-0040 and RFC-0058 permit
preflight to validate an *explicitly selected* static declaration, including
remote capability data, locally and without observation. RFC-0059 extends that
explicit static preflight input with caller-local capabilities. None says that
the historical zero-argument path selects retained topology.

RFC-0041 is more direct for status: `home-ai-cluster-status --declaration
<path>` requires one explicitly selected declaration, does not search for a
default declaration, and uses that selection to identify the remotes it will
contact. It is a finite local-plus-remote observation, not a topology resolver.
RFC-0044 preserves the required declaration, preserves default Ollama when no
runtime input is supplied, and adds only explicit local runtime composition.
RFC-0074 subsequently permits status to use one explicitly selected
`--runtime-config`, while retaining the default/explicit CLI model.

RFC-0048 changes presentation only: default human output and explicit `--json`
must preserve the existing domain result, ordering, privacy, and exit semantics.
RFC-0050 makes `hac` an additive facade and explicitly preserves delegated
command contracts.

RFC-0094 adds retained local runtime, caller-local capabilities, and remote
topology as an optional HAC-managed baseline for ordinary later invocations.
It says retained state *may* be consumed when applicable; explicit complete
topology sources replace it, and `--runtime-config` remains self-contained.
Its required proof expressly covers retained topology for ordinary
static-cluster use. It separately keeps `config show`, preflight, health, and
status as distinct surfaces, and its implementation boundary prohibits changed
routing/request/status contracts. It neither names retained preflight nor
authorizes retained status topology or status runtime selection. “May consume”
therefore describes a bounded availability of a baseline, not a universal rule
that every command must adopt it.

## 4. Current implementation and effective inputs

`static_cluster.parse_args()` loads retained configuration when no explicit
topology is selected, requires retained remotes in that case, and replaces the
default local-capability tuple with retained caller-local capabilities when
present. It separately supplies retained runtime values unless
`--runtime-config` is selected. Explicit declaration and complete inline modes
remain complete topology sources rather than patches.

`static_preflight.parse_args()` has no retained-configuration import or load.
With no declaration or complete inline pair, `main()` calls
`evaluate_static_preflight()`, which constructs the ordinary local registries
and projects `local-only`. Explicit declaration and complete inline modes call
their respective static-multi-node evaluators. Neither preflight path observes
a runtime, DNS, or network.

`status_command` requires `--declaration`, loads that declaration before
constructing status, and never imports or loads retained configuration. It
passes no retained runtime values to local composition resolution: no runtime
option retains the established Ollama default; explicit CLI values or the
explicit RFC-0074 file select composition. Only after declaration validation
does it create one HTTP client and collect local then selected remote
observations.

| Surface | Retained local runtime | Retained local capabilities | Retained remotes | Explicit topology | Network observation |
| --- | --- | --- | --- | --- | --- |
| `config show` | reports | reports | reports | n/a | no |
| `static-cluster` | baseline unless runtime file | retained topology only | baseline when no complete source | declaration/inline replaces | request-time only |
| `preflight` | ignores | ignores | ignores | declaration/inline selects static report | no |
| `health` | separate local-composition surface | n/a | ignores | n/a | local runtime only |
| `status` | ignores retained; default/explicit composition | n/a | ignores | required declaration | local + selected remotes |

The focused tests deliberately freeze these facts: preflight tests assert the
zero-argument `local-only` report and explicit declaration/inline reports;
status tests require a declaration and assert default Ollama plus explicit
runtime composition; retained-startup tests assert retained static-cluster
topology/capabilities, replacement by explicit topology, and retained runtime
override rules.

## 5. Deterministic reproduction

In an isolated configuration location, the following retained state was made
through the public command surface:

```sh
hac config local --runtime ollama --ollama-model documentation-model \
  --local-capability chat
hac config node summary-remote --base-url http://127.0.0.1:25042 \
  --capability summarize
```

`hac config show` displayed the model, local `chat`, remote identity,
loopback URL, and remote `summarize`. Parser-level static-cluster resolution
loaded that same retained topology and local restriction without starting its
foreground server. Bare `hac preflight --json` exited 0 with a coherent
`local-only` report containing local `chat, summarize`, not the retained
`chat`/`summary-remote` configuration. Explicit inline preflight with the same
documentation-only values exited 0 with `static-multi-node`, local `chat`, and
remote `summary-remote`/`summarize`. Bare `hac status --json` emitted its
argument-usage error and exited 2; it performed no network operation.

An explicit-declaration status was not run against an external endpoint: source
and tests establish that it first validates the supplied declaration, then is
the only case that constructs the finite remote observation operation.

## 6. Preflight analysis

**P1.** Bare preflight is intentionally the RFC-0036 local-only compatibility
mode in current code and tests. Retained topology is outside its current input
contract.

**P2.** Loading retained topology itself is local parsing/validation, so it
need not introduce network, DNS, runtime observation, or mutation. That fact
does not decide command meaning.

**P3–P5.** Consuming it would nevertheless change the stable bare output from
`local-only`/one local node to `static-multi-node`/retained remotes and could
make a presently successful bare command fail on malformed retained state. Both
are durable output and failure-contract changes, not incidental plumbing.

**P4.** The discrepancy with retained static-cluster local capabilities is real:
preflight currently evaluates a different selected configuration. RFC-0059
requires equivalent treatment only for explicit topology inputs; it does not
settle retained input.

**P6.** If retained preflight were later accepted, RFC-0094 already supplies
the useful narrow replacement rule: an explicit declaration or complete inline
topology replaces retained topology rather than merging. The decision to make
retained topology applicable to preflight remains missing.

**Classification: P-D — accepted contracts are ambiguous; RFC required to
resolve.** RFC-0094’s broad “ordinary invocations may consume” wording leaves
room for retained preflight, while RFC-0036’s stable zero-argument mode and
RFC-0094’s absence of a preflight authorization do not choose it. The smallest
decision question is: *When retained topology exists and no explicit topology
is supplied, should bare static preflight inspect that retained effective static
topology, or preserve its historical local-only contract?*

## 7. Status topology analysis

**S1–S2.** Required `--declaration` is an accepted status authority contract,
not parser residue. RFC-0041 ties the selected declaration to the identities
and endpoints it observes. Invoking `status` explicitly is not the same as
selecting a stored topology for this invocation. Retained endpoints were
selected earlier for static-cluster startup; making bare status contact them
would add a new invocation-time network-authority source.

**S4–S6.** RFC-0094’s complete-topology replacement helps only after a retained
status topology has been accepted; it does not define how a required declaration
would become optional. Changing bare status from usage error/exit 2 to live
observation is material compatibility and authority change. Privacy-safe output
would not cure that authority change.

**Classification: S-T-A — current explicit declaration should remain.** This
is explicit in RFC-0041 and preserved by RFC-0044 and RFC-0094. Documentation
can clarify the distinction; no implementation gap exists. Any future change
requires a separate RFC asking whether bare status may select retained topology
as its network-observation target.

## 8. Status local-runtime analysis

RFC-0044 deliberately makes no-runtime-option status Ollama-backed and makes
alternative composition explicit. RFC-0074 adds explicit file selection. RFC-0094
does not supersede either input-source rule and explicitly forbids changing
status contracts in its implementation boundary. Thus `hac status -d file`
with no runtime option must not silently begin observing a retained
llama-server composition.

**Classification: S-R-A — current explicit/default composition semantics should
remain.** This is already decided rather than merely undocumented. A future
different question—whether status may use retained runtime while retaining an
explicit declaration—would require its own RFC; it must not be bundled with
status-topology selection.

## 9. Operator documentation and options

Current README/getting-started/configuration examples and the canonical workflow
describe explicit declaration paths for static preflight and status. The command
reference says status inspects one declared cluster and lists only declaration
forms. The workflow still uses older “retained declaration” language for an
operator-owned declaration file, which can be confused with RFC-0094 HAC-managed
state. It does not yet explain that `hac config ...` establishes a retained
baseline for static-cluster but not for preflight/status. That is the principal
operator-experience gap.

| Option | Shape | Assessment |
| --- | --- | --- |
| A | retained static-cluster; explicit preflight/status | Contractually coherent today; document the three different selection rules. |
| B | retained preflight; explicit status | Principled network-free split, but changes bare preflight output/failures and needs the P decision RFC. |
| C | retained preflight and status | Adds both the P decision and a new status network-authority/compatibility decision; not authorized. |
| D | retain status runtime only | Conflicts with explicit/default RFC-0044/RFC-0074 semantics and needs a separate RFC; no evidence supports it. |

Option A is sufficient for 1.0 once the documentation explicitly distinguishes
retained facts, static-cluster startup baseline, static preflight selection, and
status’s explicit observation target. This investigation does not make that
documentation change.

## 10. Recommended next steps and non-goals

1. Clarify current operator documentation, without changing command semantics:
   retained configuration is used by ordinary static-cluster startup, whereas
   preflight takes local-only or explicitly supplied topology and status requires
   an explicit declaration.
2. Do not implement retained preflight. If product evidence requires it, first
   decide the narrow P question above in an RFC.
3. Keep status topology and status runtime explicit. No RFC or implementation
   work is currently needed for either.

This record does not authorize an RFC, command change, automatic declaration
lookup, retained-status observation, retained-status runtime resolution,
generic precedence system, profiles, discovery, health broadening, networking,
or test changes.
