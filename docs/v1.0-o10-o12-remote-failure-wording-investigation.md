# O-10 and O-12 Remote Failure Wording Investigation

Status: Investigation record

## 1. Status and scope

This is a documentation-only investigation of O-10 and O-12 from the 1.0
two-node operator validation. It changes no runtime, HTTP, CLI, routing,
retry, fallback, configuration, test, or RFC behavior. It preserves the O-13
containment of caused `RemoteTransportError` instances before ASGI logging.

The investigation started from clean `main` at
`3bb39fcd9b64429c51041323036b80932cd14a21`, the expected merge result after
PR #626. All reproduction evidence below uses synthetic text, `remote-node`,
and loopback/ASGI transports; no operator endpoint, host, prompt, response, or
model inventory is retained.

## 2. Real observations

| Finding | Receiver state | Caller CLI result | Functional result |
| --- | --- | --- | --- |
| O-10 | HAC process absent | `error: runtime adapter unavailable`, exit 1 | no fallback/retry; caller lived and recovered |
| O-12 | HAC reachable; selected runtime absent | `error: ordinary request failed`, exit 1 | no fallback/retry; both processes recovered |

These are different failure shapes. O-10 is a connection failure from caller to
receiver HAC. O-12 reaches receiver HAC and gets its selected-runtime failure.

## 3. Accepted contracts

- RFC-0007 keeps runtime-specific availability inside adapters and exposes only
  normalized runtime unavailability to public layers.
- RFC-0013 and RFC-0014 require remote transport to return a normalized result,
  transport failure, or runtime failure. They deliberately leave status and
  user-facing mapping open, but distinguish a failure carrying a request from
  a receiver runtime failure.
- RFC-0028 allows candidate advance only for the affirmative pre-request
  connection-unavailable condition; status, timeout, and ambiguous failures
  remain visible without another attempt.
- RFC-0038 and RFC-0040 require ordinary remote transport failures to be
  normalized, prohibit endpoint/raw-transport exposure, and preserve the same
  no-retry/no-further-remote rule after post-connect failure.
- RFC-0034 has a deliberately local-only structured actual-request vocabulary.
  Its `runtime-unavailable` includes the pre-transmission subtype, while its
  `execution-failed` hides raw transport detail. It expressly excludes remote
  failure protocols, so it is not itself a public cross-node protocol.
- RFC-0045 fixes the ordinary Chat client’s stable mapping: public HTTP 503 is
  `error: runtime adapter unavailable`; unexpected statuses are
  `error: ordinary request failed`. RFC-0051, RFC-0054, RFC-0060, RFC-0061,
  RFC-0067, and RFC-0077 reuse the ordinary capability/transport boundary; the
  native clients share this status vocabulary. RFC-0082 preserves terminal
  results/exceptions and adds neither retry nor a new failure category.

Thus 503 currently has an exact ordinary-client phrase, even though the
remote-transport RFCs did not define it as a remote-node diagnosis.

## 4. Failure pipeline

For an ordinary remote Summarize request, `summarize_command._send_native_request()`
posts to caller `/v1/summarize`; its `_failure_for_status()` maps 503 specially
and every other non-success status generically. `api.routes.summarize()` builds
`SummarizeRequest`, enables remote eligibility only in static composition, and
uses `run_routable_execution()` to call `handle_summarize_cluster_request()`.
That invokes `orchestrate_request_with_*static_remote_fallback()`, selection,
and `execute_declared_remote_routing_candidate()`.

`HttpRemoteTransport.send()` serializes the closed envelope with
`internal_cluster_request_body()`, posts to
`/internal/cluster/request`, then calls `response.raise_for_status()` before it
validates a result. The receiver route validates that envelope and calls
`handle_static_local_cluster_request()`. Its local adapter’s
`RuntimeAdapterUnavailableError` becomes HTTP 503 with
`{"detail":"Runtime adapter unavailable"}`.

| Boundary | O-10 output | O-12 output | Preserved / intentionally hidden |
| --- | --- | --- | --- |
| remote HTTP client | `httpx.ConnectError` | receiver HTTP 503 then `httpx.HTTPStatusError` | declaration and endpoint remain internal |
| `HttpRemoteTransport.send()` | `RuntimeConnectionUnavailableBeforeRequestError` | `RemoteTransportError` | both messages are categorical; cause retains HTTPX detail only internally |
| routing/executor | same exception, no next candidate | same exception, no next candidate | selected declared node remains internal routing context |
| caller route / O-13 handler | HTTP 503 JSON runtime detail | HTTP 500 plain `Internal Server Error` | O-13 deliberately hides remote body, cause, URL, and traceback |
| ordinary CLI | runtime-adapter phrase | generic ordinary-request phrase | response bodies are not exposed |

The caller public handler chooses O-10’s 503 by catching
`RuntimeAdapterUnavailableError` (the connection exception is its subtype) in
`handle_summarize_cluster_request()`. O-13’s app-wide
`_remote_transport_error_response()` instead maps an escaping
`RemoteTransportError` to privacy-safe 500. The terminal clients then apply
their exact status map. Chat and source-grounded Chat share
`chat_command._failure_for_status()`; Summarize and Classify duplicate the same
422/404/503/generic logic; Code delegates to the Chat mapper.

## 5. Deterministic reproductions

### O-10: selected remote HAC unreachable

The focused loopback transport reproduction uses a caller static composition
with only `remote-node` eligible for Summarize and an `httpx.ConnectError` from
the real `HttpRemoteTransport` request. `tests/test_remote_transport.py` proves
the transport produces `RuntimeConnectionUnavailableBeforeRequestError` with
the safe message `Remote connection unavailable before request transmission`.
`tests/test_static_cluster.py::test_static_cluster_normalizes_exhausted_connection_failures`
then exercises caller routing and HTTP edge: one remote attempt produces HTTP
503 and `{"detail":"Runtime adapter unavailable"}`. The existing ordinary
Summarize client test maps that 503 to the observed stderr line and exit 1.

The first semantic change is therefore not an accidental loss: the narrow
remote-HAC connection condition is intentionally represented by the existing
pre-transmission runtime-unavailable subtype, and the public 503 is then
required by the current ordinary-client contract to use runtime wording.

### O-12: reachable remote HAC, unavailable receiver runtime

The O-13 loopback receiver reproduction starts an ASGI receiver whose real
`/internal/cluster/request` boundary returns the local runtime-unavailable 503
shape. `tests/test_remote_transport.py::test_http_remote_transport_raises_normalized_error_for_http_failure`
exercises `raise_for_status()` and proves that a receiver 503 becomes
`RemoteTransportError("HTTP remote transport could not send request")`.
The O-13 routed-family containment test then exercises caller routing plus the
app-wide exception handler: caller response is HTTP 500, plain
`Internal Server Error`, with one remote request and no leak. The normal
Summarize client mapping correctly converts that 500 to
`error: ordinary request failed`, exit 1.

The first semantic loss is `HttpRemoteTransport.send()`: it calls
`raise_for_status()` before inspecting the normalized receiver failure and
collapses receiver runtime HTTP 503 with malformed/status/protocol failures
into `RemoteTransportError`. O-13 containment correctly preserves privacy but
can only map that already-generic error to 500; it is not the first loss and
must not expose the receiver’s raw body or exception cause.

## 6. Current status matrix

| Failure | Receiver/internal status | Caller/public status | CLI text |
| --- | ---: | ---: | --- |
| loopback cluster unavailable | n/a | n/a | ordinary cluster unavailable |
| no capability | n/a | 404 | no available `<capability>` capability |
| local runtime unavailable | n/a | 503 | runtime adapter unavailable |
| remote HAC unreachable | transport / pre-transmission | 503 | runtime adapter unavailable |
| remote runtime unavailable | 503 | 500 after O-13 containment | ordinary request failed |
| generic remote protocol failure | varies / invalid result | 500 after O-13 containment | ordinary request failed |

The implementation, rather than RFC-0013/0014, chooses these internal HTTP
statuses. RFC-0045 freezes the present native reading of caller 503. The
structured RFC-0034 vocabulary is an explicit local operator surface and does
not alter this matrix.

## 7. Privacy and compatibility

The accepted contracts permit the smallest cluster-owned categorical outcome;
they forbid raw remote response body, HTTPX/socket text, traceback, prompt,
model, adapter/runtime detail, endpoint URL, hostname, IP, and private node
identity on ordinary public failure surfaces. A caller’s selected node ID is
available internally for routing explanation, but is not presently carried to
an ordinary CLI failure and must not be assumed safe to disclose.

HTTP status and exact ordinary CLI strings are candidate-facing compatibility
surfaces under RFC-0045 and the 1.0 CLI candidate investigation. Internal
exception classes and routing context are implementation details except where
their accepted semantics are explicitly specified. The internal endpoint is
an accepted narrow protocol boundary; changing its failure schema is not
automatically free.

## 8. Candidate resolutions

| Option | O-10 | O-12 | Finding |
| --- | --- | --- | --- |
| A. wording only | Changing 503 wording conflicts with RFC-0045 and also weakens truthful local-runtime wording | cannot recover 503 from caller 500 | insufficient |
| B. preserve remote runtime category | unrelated | receiver 503 can remain a safe categorical runtime failure through transport and caller edge | authorized correction |
| C. distinct remote-node-unavailable category | useful but absent from accepted public/remote protocol taxonomy | not needed | RFC required |
| D. document current state | technically bounded but leaves misleading O-10 / lost O-12 meaning | technically bounded but loses an accepted distinction | not recommended |
| E. generic selected-execution wording | changes the accepted 503 phrase and sacrifices local specificity | only works after B | needs a compatibility/product decision |

## 9. Classifications and next step

**O-10 classification: O10-D — RFC required.** The current behavior is
consistent with the accepted pre-transmission subtype and RFC-0045’s exact 503
phrase. A distinct privacy-safe “remote node/application unavailable” outcome,
or a changed generic 503 phrase, is a new durable public failure/protocol or
compatibility decision. It is not authorized as a wording-only correction.

**O-12 classification: O12-C — implementation semantic correction authorized.**
RFC-0013/0014 already require the remote boundary to distinguish normalized
runtime failure from transport failure. A reachable receiver’s existing safe
runtime 503 is discarded before caller containment. A narrow implementation
that preserves only the accepted categorical runtime-unavailable result through
the existing transport and maps it at the caller public edge to the existing
503 behavior is authorized; it does not require a new public category or raw
error propagation, and it must retain O-13’s safe generic handling for every
other `RemoteTransportError`.

The smallest next action is a separate O-12 implementation PR with focused
receiver-503, caller-503, CLI, and O-13 regression tests. It must preserve
route selection, no fallback, no retry, 500 containment for unknown remote
failures, and all privacy redactions. Open a narrow RFC only if the project
also wants the separate O-10 remote-HAC-unavailable category or to change the
accepted generic meaning of ordinary 503.

## 10. Non-goals

This investigation does not propose an error hierarchy, new fields, endpoint
schema, health model, node targeting, retry, fallback, remote lifecycle,
discovery, logging, or a change to O-11’s declared-versus-observed health
clarity issue.
