# O-13 Remote Failure Traceback Investigation

Status: Investigation record

## Scope and starting point

This is a documentation-only investigation of O-13 from the 1.0 two-node
operator validation: an expected remote runtime failure escaped the caller's
ordinary static-cluster HTTP edge as `RemoteTransportError` and Uvicorn emitted
an ASGI traceback. It does not change runtime behavior, CLI behavior, HTTP
contracts, fallback, or failure taxonomy.

The investigation started from `main` at
`8cbf77e73c8f6789528f4d8f60303361b7b68e4f` (the merge commit after PR #620).
The real validation record remains privacy-safe: this document uses only
loopback endpoints and does not retain real addresses, paths, request content,
or generated content.

## Accepted boundaries consulted

- RFC-0013 requires the remote transport boundary to return a normalized
  cluster result or normalized transport/runtime failure; it deliberately
  leaves user-facing error mapping open.
- RFC-0014 makes the internal HTTP request `POST /internal/cluster/request`
  carry normalized requests/results/failures, but likewise does not choose
  status-code or user-facing error mapping.
- RFC-0028 permits fallback only for the affirmative pre-request connection
  condition. HTTP status failures and other post-connect/ambiguous failures
  remain visible and must not cause another attempt.
- RFC-0038 requires the ordinary remote adapter to normalize transport,
  timeout, remote-HTTP, and invalid-response failures; it must never expose a
  remote base URL in public errors and ordinary static mode must preserve its
  privacy boundary.
- RFC-0040 extends that rule to ordered remotes: advance only on the same
  pre-request connection condition and do not expose raw transport errors or
  private endpoints through ordinary logs or public responses.
- RFC-0051, RFC-0061, and RFC-0077 place Summarize, Classify, and
  source-grounded Chat respectively on the existing capability routing and
  internal transport boundary. RFC-0077 explicitly adds no special public
  transport-failure taxonomy.
- RFC-0082 makes `run_routable_execution()` the disconnect-cancellation seam
  for the ordinary Chat, source-grounded Chat, Summarize, Classify, and
  internal receiver routes. It preserves a completed execution's terminal
  exception/result and creates no retry or fallback authority.

## Current exception path

On the receiving ordinary HAC application, `/internal/cluster/request`
revalidates the normalized envelope and executes it locally. When its runtime
adapter is unavailable, `handle_static_local_cluster_request()` catches
`RuntimeAdapterUnavailableError` and returns HTTP 503 with the safe detail
`Runtime adapter unavailable`. Thus the receiver-generated 503 is a normal
receiver-local runtime-unavailable response, not a caller transport failure.

On the caller, `HttpRemoteTransport.send()` posts that normalized request and
then calls `response.raise_for_status()`. The receiver's 503 becomes
`httpx.HTTPStatusError`; the `except httpx.HTTPError` clause raises
`RemoteTransportError("HTTP remote transport could not send request")` from it.
The exception is normalized at the core transport boundary, but its original
HTTPX exception remains its Python cause for diagnostics.

`execute_declared_remote_routing_candidate()` and both static orchestration
functions deliberately let that error propagate. This preserves RFC-0028 and
RFC-0040: it is post-connect, so it is neither retried nor sent to another
remote. The gap is at the caller's public route handlers:

- `handle_chat_cluster_request()` catches only
  `RuntimeAdapterUnavailableError` and `NoSelectableRoutingCandidateError`.
- `handle_summarize_cluster_request()` catches those same errors.
- `handle_classify_cluster_request()` catches those plus
  `InvalidClassificationLabelError`.
- source-grounded Chat delegates to `handle_chat_cluster_request()`.

None catches `RemoteTransportError`. It therefore crosses
`run_routable_execution()` and the FastAPI route boundary. FastAPI returns its
default 500 body while Uvicorn logs the unhandled exception chain, including
the original request URL and stack frames. The transport's short public
exception message alone is safe; retaining its cause is what makes allowing it
to reach the ASGI logger a privacy leak.

## Capability and wiring matrix

| Request family | One remote | Ordered remotes | Public result today | Traceback / further remote |
| --- | --- | --- | --- | --- |
| Chat | Remote status failure propagates. | Same common ordered executor. | HTTP 500, `Internal Server Error`. | Uvicorn traceback; stop immediately. |
| Summarize | Remote status failure propagates. | Same common ordered executor. | HTTP 500, `Internal Server Error`. | Uvicorn traceback; stop immediately. |
| Classify | Remote status failure propagates. | Same common ordered executor. | HTTP 500, `Internal Server Error`. | Uvicorn traceback; stop immediately. |
| Source-grounded Chat | Uses the Chat handler and transport. | Same common ordered executor. | HTTP 500, `Internal Server Error`. | Uvicorn traceback; stop immediately. |

The matrix applies when caller-local static capability declaration makes the
selected capability remote-eligible and the local candidate ineligible. It is
therefore intrinsic to the common remote transport/public-route boundary, not
to retained configuration. Retained topology merely supplies the same ordered
collection wiring used by declaration-backed topology. There is no retry in any
row. A pre-request `ConnectError` is separately normalized to
`RuntimeConnectionUnavailableBeforeRequestError` and is the sole condition
that can advance the existing ordered traversal.

## Deterministic loopback reproduction

A disposable, untracked loopback-only helper started:

1. a fake receiver at `127.0.0.1` whose internal request route returned the
   receiver's safe runtime-unavailable HTTP 503 shape;
2. a caller static-cluster FastAPI/Uvicorn process whose local declaration made
   the requested capability ineligible and whose remote declaration made it
   eligible; and
3. ordinary caller requests for Summarize and Chat.

The Summarize and Chat calls each produced caller HTTP 500 with body `Internal
Server Error`, one receiver `POST /internal/cluster/request` with HTTP 503,
and a caller Uvicorn `Exception in ASGI application` traceback containing the
sanitized exception sequence `HTTPStatusError` then `RemoteTransportError`.
The caller access line for each failed request was `500 Internal Server Error`.

A second run used an ordered two-remote collection. The first loopback receiver
returned 503 and a second loopback receiver was ready to return success. The
caller returned HTTP 500 and the first receiver recorded exactly one request;
the second receiver recorded none. This confirms that the status failure does
not silently retransmit to another candidate.

Classify and source-grounded Chat were not separately run as subprocesses:
their routes call the same static orchestration boundary as the live cases;
source-grounded Chat shares the exact Chat handler, while Classify differs only
in success-result validation after transport completion. Focused existing tests
exercise their closed envelopes and shared route/disconnect coverage.

## Existing tests and the missing assertion

`tests/test_remote_transport.py` explicitly verifies that an HTTP 503 becomes
`RemoteTransportError`. `tests/test_ordered_remote_fallback.py` verifies that a
Summarize `RemoteTransportError` stops at the first remote. Route, source-
grounded, and client-disconnect tests cover the common request paths and show
that all accepted routable families use `run_routable_execution()`.

`test_static_cluster_hides_remote_base_url_from_public_transport_failure`
injects a `RemoteTransportError`, uses ASGI transport with
`raise_app_exceptions=False`, and asserts HTTP 500 with `Internal Server Error`
and no private URL in the response. It is valuable response-body coverage, but
it records framework handling rather than an intentional accepted public-500
contract: it neither runs Uvicorn nor captures server logs. It cannot detect
the traceback/cause leakage.

## Client-disconnect and loopback-browser boundaries

`run_routable_execution()` creates one execution task and one disconnect
observer. If execution finishes first, it awaits that task and preserves the
same exception identity; it neither converts, consumes, nor duplicates
`RemoteTransportError`. A disconnect can cancel pending work before a result is
owned, but no disconnect occurred in the reproduction. It does not explain the
failure or a successful access line.

The static-cluster entry point adds loopback browser routes only when composing
the app. The failing native `/v1/summarize` and `/v1/chat` paths neither pass
through browser request composition nor receive a browser-generated response.
It does not materially participate in O-13.

## The observed `200 OK` anomaly

For each correlated live failed request, the sole caller access line was HTTP
500 and it was followed by the ASGI traceback. No failed request produced a
caller `200 OK` line. The preliminary receiver-readiness `GET /docs` lines were
separate requests and were logged as 200, demonstrating why adjacent access
lines are not sufficient correlation.

The historical `POST /v1/summarize ... 200 OK` cannot be attributed from the
retained observation. This investigation establishes only that an individual
unhandled `RemoteTransportError` request does not reproduce as both the ASGI
traceback and `200 OK`; the earlier 200 therefore belongs to another request
or cannot be explained without unavailable correlation evidence. It must not
be treated as response-start timing or browser behavior.

## Contract analysis and classification

`RemoteTransportError` is already the normalized core transport failure
required by RFC-0013/RFC-0014. Core normalization is not the same job as safe
normalization at the caller's public HTTP edge. RFC-0038 and RFC-0040 already
require remote HTTP failures to be normalized and prohibit raw transport errors
and private endpoints in ordinary public/logging surfaces. Allowing the caused
exception to reach Uvicorn violates that accepted privacy/error boundary.

**Classification: Mixed conclusion.**

- **O-13 traceback/log leak: A — implementation defect against accepted
  contracts.** A follow-up implementation PR is authorized to contain
  `RemoteTransportError` at the shared ordinary static request HTTP boundary
  (or a demonstrably equivalent common route seam) before it reaches FastAPI /
  Uvicorn. It must preserve the no-retry/no-further-remote behavior.
- The existing caller-visible HTTP 500 / `Internal Server Error` outcome can be
  preserved by that narrow repair; the current test is useful regression
  evidence but does not make the framework default an accepted durable mapping.
- RFC-0013/RFC-0014 do not decide an exact public status/body for a selected
  remote transport failure, nor a durable distinction among unreachable HAC,
  reachable HAC with unavailable runtime, and generic post-connect failure.
  Richer wording, status, or taxonomy would be a separate O-10/O-12 contract
  question and may require RFC work. It is not required to stop this leak.

## Recommended next step and non-goals

Create one narrow implementation PR that adds focused Uvicorn/log-capture
regression coverage and contains `RemoteTransportError` at the ordinary static
HTTP boundary without changing response semantics, candidate traversal,
retries, runtime health, CLI wording, or remote topology. It should verify all
four ordinary routable families through the shared seam.

This investigation does not authorize a new failure taxonomy, changed public
status/body, changed CLI output, fallback redesign, retransmission, logging
expansion, browser redesign, or an RFC. No implementation or RFC change is
included here.
