# 1.0 O-14 Bare Config Discovery Investigation

Status: Investigation

## 1. Scope

This investigation considers only bare `hac config` and its equivalent
`home-ai-cluster config` spelling. It asks whether that namespace-only
invocation may present config help on stdout with exit 0 before 1.0.

It does not change implementation, tests, CLI behavior, retained configuration,
or RFCs. It does not consider an implicit `show`, a wizard, prompts, TTY
behavior, environment, runtime, node, or plugin discovery, or malformed
concrete actions.

## 2. Starting main

Investigation started from clean `main` at
`c6621632b322189da6fdc4e6f38f2b3bf2f02ac4` (merged PR #624).

## 3. Operator observation

The two-node validation records O-14: bare `hac config` is an argparse usage
error, while `hac config -h` presents the useful config command map. It records
the narrow follow-up question and keeps incomplete concrete actions as errors.

## 4. Accepted contracts

RFC-0050 makes bare root invocation successful static discovery, but its exact
grammar and success rule are root-specific. It is a useful analogy, not a
general nested-namespace rule. Its delegation rule preserves the selected
command's behavior; it does not make every later implementation detail of a
newly added delegated command immutable.

RFC-0052 requires `hac` and `home-ai-cluster` to use the same root entry point
and preserve equivalent behavior. Any later O-14 refinement must therefore
apply to both spellings.

RFC-0094 defines the bounded `config local`, `config node`, and `config show`
surfaces, their authority, and retained-state boundaries. It specifies no
meaning for bare `config`; its only inspection operation is explicit
`config show`. RFC-0095 and RFC-0096 add bounded configuration facts while
leaving the exact finite config spelling open to implementation. None requires
bare config to fail or to print help.

RFC-0092 adds root-only `-h` and keeps existing argparse subcommand help. It
does not decide bare config.

The 1.0 CLI candidate calls the six concrete config subcommands candidate-stable
and classifies accepted parser/input misuse as exit 2, but expressly does not
freeze every parser implementation detail or help line. It does not classify
the namespace-only invocation itself. The diagnostics investigation records the
existing general argparse model; it does not separately analyze bare config.

## 5. Current implementation and tests

`config_command._create_argument_parser()` creates a required argparse
subparser. `config_command.main()` parses before any retained-state operation,
so an empty config argument list errors without reading or writing state. The
root dispatch table passes remaining arguments unchanged to that function.

`tests/test_config_command.py::test_config_requires_one_of_the_bounded_surfaces`
deliberately asserts the current empty-list exit 2 and stderr usage. The test
was introduced with the retained-config implementation in commit `9181795`
(`Add retained configuration CLI`), after RFC-0094 accepted the architecture.
It is focused pre-1.0 implementation behavior, not evidence of an accepted
architectural decision about namespace discovery.

## 6. Deterministic reproduction

With isolated empty `XDG_CONFIG_HOME` and `HOME`, current checkout behavior is:

| Invocation | Stdout | Stderr | Exit | Role |
| --- | --- | --- | ---: | --- |
| `hac` | root help | empty | 0 | discovery |
| `hac --help` | root help | empty | 0 | discovery |
| `hac config` | empty | argparse usage/error | 2 | current O-14 behavior |
| `hac config --help` | config help | empty | 0 | config discovery |
| `hac config -h` | config help | empty | 0 | config discovery |
| `hac config show` | retained-state report | empty | 0 | explicit read-only action |
| `hac config unknown` | empty | argparse usage/error | 2 | invalid subcommand |
| `hac config local` | empty | argparse usage/error | 2 | incomplete action |
| `hac config node` | empty | argparse usage/error | 2 | incomplete action |
| `home-ai-cluster config` | empty | argparse usage/error | 2 | long-root equivalent |

The two help forms construct only argparse help. Bare config already exits
before retained-state loading; a later help-only branch at that same seam can
remain equally authority-free.

## 7. Namespace versus action

Bare `config` selects no operation. Treating it as discovery is narrowly
consistent with bare root discovery and does not conflate it with `config show`:
the latter reads and reports HAC-managed retained facts. Once `local`, `node`,
`external-information`, `chat`, `reset`, or `show` is selected, existing
missing, invalid, or unknown input remains an argparse or local-validation
error.

## 8. Candidate resolutions

**A — preserve stderr/2.** This preserves the current focused test, but leaves
the observed discovery friction. Documentation could point to `config -h`, but
would not make the namespace match the root's discovery role.

**B — bare namespace discovery.** `hac config` and `home-ai-cluster config`
could print the existing config help to stdout and return 0, without state,
runtime, network, plugin, or mutation activity. A small command-specific branch
before `parse_args()` can preserve every concrete parser path. This is a
presentation/discovery refinement for an accepted namespace, not a new
configuration, authority, interaction, or ownership model.

**C — implicit `show`.** Rejected: even read-only `show` reads retained state
and has a distinct accepted inspection meaning.

**D — wizard or menu.** Out of scope: it introduces an interaction model and
would exceed this bounded discovery question.

## 9. RFC threshold and classification

**O14-B — discovery refinement already compatible.** No RFC is required. The
accepted contracts define the root, concrete config operations, retained-state
authority, and root parity, but leave bare config unspecified. Changing only
that no-operation invocation before 1.0 is a small product/discovery refinement
with a visible compatibility effect that focused tests and documentation should
make explicit; it does not change architecture or accepted retained-state
semantics.

## 10. Recommended next step

Submit one small implementation/test/documentation PR that makes only empty
config arguments print the existing config help and return normally. It should
update the focused bare-config expectation; add root-facade parity and
no-retained-state-access coverage; retain stderr/2 for unknown and incomplete
concrete forms; and add the smallest discovery note if needed.

## 11. Non-goals

No implementation is authorized by this investigation. It does not authorize a
wizard, implicit action, TTY behavior, configuration-file editing, profiles,
environment or runtime/node/plugin discovery, network activity, parser
refactoring, or any change to malformed concrete invocations.
