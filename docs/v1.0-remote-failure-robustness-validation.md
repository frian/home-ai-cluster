# Home AI Cluster 1.0 Remote Failure Robustness Validation

Status: Evidence record

Date: 2026-09-05

This document records a factual manual robustness validation of the published
Home AI Cluster `1.0.0` release. It exercises already accepted timeout,
disconnect, remote-failure, and ordered-fallback behavior. It introduces no
feature or architectural change.

The testing rule was:

> Observe. Reproduce. Record. Fix only real bugs.

## Test topology

The caller/orchestrator ran on `sat` with the published HAC `1.0.0` release.
The ordinary static-cluster process exposed caller-local `chat` and declared
remote `summarize` capability on Debian Incus containers running Ollama with
`llama3.2:1b`.

The primary receiver was `hac-debian-2`, exposed through the host proxy origin:

```text
http://192.168.1.9:25044
```

A second receiver, `hac-debian-1`, was used for the ordered fallback proof and
was exposed through:

```text
http://192.168.1.9:25043
```

The receiver process itself listened on container loopback port `25042`; Incus
host proxy devices provided the host-visible origins above.

## Validation scenarios and observed results

### 1. Caller-owned timeout during remote execution

A deliberately long remote `summarize` request was issued with a one-second
caller timeout.

The CLI returned:

```text
error: ordinary request timed out
exit=1
```

No traceback was emitted.

An immediate subsequent remote `summarize` request completed successfully on:

```text
node_id = "receiver"
adapter = "ollama"
model = "llama3.2:1b"
```

This demonstrates bounded caller failure and immediate HAC-path recovery after
a caller-owned timeout.

It does not establish that the downstream runtime stops generation at the same
moment as the caller timeout.

### 2. Downstream runtime activity after caller timeout

A second timeout observation used a five-second caller timeout so that remote
model execution could clearly begin before the caller returned.

Receiver-side process observation showed the Ollama `llama-server` runner
becoming CPU-active before the timeout and remaining CPU-active for several
seconds after the caller had already returned. The runner then returned to an
idle state.

This is recorded as real operational evidence that:

```text
caller timeout
!=
downstream runtime resource release
```

This is consistent with the accepted RFC-0082 boundary: HAC cancels and
releases its own pending request ownership on confirmed disconnect, while
runtime- and transport-level termination remains best-effort and
adapter-dependent.

No runtime-specific cancellation guarantee is inferred from this observation.

### 3. Operator interrupt of a finite remote CLI request

A long remote `hac summarize` request was interrupted with `Ctrl-C` at the
finite caller CLI while the static-cluster process and remote receiver remained
running.

The shell exit status was:

```text
130
```

The released `1.0.0` CLI also exposed a full Python `KeyboardInterrupt`
traceback. This was classified as a real operator-facing CLI presentation bug,
not an architectural or routing failure.

The next remote `summarize` request completed successfully on the same receiver
without restarting the caller/orchestrator or receiver.

A separate Draft PR, #676, isolates a minimal root-command interruption fix. It
is not part of this evidence record and was not required to validate the
released cluster recovery behavior.

### 4. Graceful receiver shutdown waits for active work

During an active remote request, one `Ctrl-C` was sent to the foreground
receiver process.

Uvicorn entered graceful shutdown and reported that it was waiting for active
connections to close. The receiver did not immediately disappear while the
request was still active.

This first observation therefore did not test abrupt receiver loss. It records
only that the foreground server attempts to drain active work on its first
interrupt.

### 5. Forced receiver termination during an in-flight request

The receiver was then tested with a second `Ctrl-C` during graceful shutdown,
forcing termination while a remote request was already in flight.

The caller returned:

```text
error: ordinary request failed
exit=1
```

The caller did not expose a traceback and did not wait for its 120-second
request timeout.

After the receiver was restarted, a new remote `summarize` request completed
successfully on the same receiver.

The forced server shutdown emitted Uvicorn/FastAPI/asyncio cancellation and
`KeyboardInterrupt` traceback logging on the receiver side. This evidence does
not classify those logs as a HAC protocol defect: the test intentionally forced
ASGI task termination rather than performing a graceful shutdown.

### 6. Ambiguous post-transmission failure does not replay on another remote

Two explicit remote nodes were declared with `summarize` in declaration order:

```text
receiver-1 = hac-debian-2
receiver-2 = hac-debian-1
```

A baseline request confirmed normal static precedence on `receiver-1`.

A second long request was allowed to begin execution on `receiver-1`, after
which that receiver was force-terminated.

The caller returned:

```text
error: ordinary request failed
exit=1
```

The `receiver-2` server log showed no corresponding:

```text
POST /internal/cluster/request
```

for the failed request.

This demonstrates the released fail-closed boundary for an ambiguous or
post-transmission failure: HAC did not replay the same request on the next
remote candidate.

This is the important safety distinction from ordinary pre-transmission
fallback and is consistent with RFC-0028.

### 7. Incus proxy can preserve TCP reachability after backend receiver loss

After `receiver-1` was stopped behind its Incus host proxy, a new request did
not automatically continue to `receiver-2`; it returned:

```text
error: ordinary request failed
```

The host proxy port remained present even though the backend HAC receiver was
no longer running. The caller could therefore reach an intermediary before the
backend failure became visible.

This means the observed failure could not be treated as an affirmative
connection failure before request transmission.

Operationally, the lab demonstrated:

```text
backend receiver unavailable behind a still-listening proxy
!=
caller cannot connect to the declared origin
```

The proxy can therefore turn an otherwise simple backend outage into an
ambiguous transport failure from HAC's point of view. This observation does not
change HAC routing semantics.

### 8. Affirmative pre-transmission failure advances ordered fallback

To test the actual pre-transmission fallback boundary, the first declared
remote was changed to an origin with no listener:

```text
http://192.168.1.9:25999
```

The second declared remote remained the live `receiver-2` endpoint.

A new `summarize` request completed successfully with:

```text
node_id = "receiver-2"
```

This demonstrates the complementary released behavior:

```text
affirmative pre-transmission connection failure
-> ordered fallback may advance
```

while the previous scenario demonstrates:

```text
ambiguous or post-transmission failure
-> terminal failure, no replay
```

### 9. Complete node loss during an in-flight request

The primary receiver container was force-stopped with Incus while a long remote
request was in progress.

The caller returned:

```text
error: ordinary request failed
exit=1
```

No caller traceback was emitted.

The container was then restarted, the HAC receiver was started again, and a new
remote request completed successfully with:

```text
node_id = "receiver"
adapter = "ollama"
model = "llama3.2:1b"
```

This demonstrates clean caller failure and recovery after complete loss and
return of a declared remote node, without restarting the caller/orchestrator.

## Consolidated result

The published `1.0.0` behavior was manually validated for:

- bounded caller timeout with clean CLI failure;
- immediate subsequent remote-request recovery;
- operator interruption of a finite caller command;
- receiver graceful shutdown behavior;
- forced receiver loss during an in-flight request;
- terminal handling of ambiguous post-transmission failure;
- absence of replay on a second declared remote after ambiguous failure;
- safe ordered fallback after affirmative pre-transmission connection failure;
- complete remote-node loss during in-flight work;
- recovery after the remote node returns.

The only concrete product defect found during this campaign was the root CLI
`KeyboardInterrupt` traceback on operator `Ctrl-C`; it is isolated separately
in Draft PR #676.

No architectural defect was found.

## What this validation does not establish

This evidence does not establish:

- guaranteed downstream runtime cancellation after caller timeout or disconnect;
- immediate CPU, GPU, memory, socket, or model-resource release;
- load balancing or generic scheduling;
- execution-availability or runtime-capacity awareness;
- retries after ambiguous transmission;
- exactly-once distributed execution semantics beyond the tested no-replay
  boundary;
- network-partition, packet-loss, proxy-reset, or asymmetric-failure behavior in
  general;
- streaming cancellation or partial-response semantics;
- authentication, authorization, confidentiality, or peer identity;
- Windows receiver failure behavior;
- dynamic discovery or dynamic membership.

The validation is deliberately bounded to already released 1.0 behavior and
records only the failure and recovery paths observed in this manual test
campaign.
