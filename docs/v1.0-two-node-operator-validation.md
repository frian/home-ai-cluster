# 1.0 Two-Node Operator Validation

Status: Evidence record

## Purpose and boundary

This is a privacy-safe record of a real home-LAN operator validation of the
Home AI Cluster 1.0 candidate. It records observations made before focused
follow-up investigations begin. It is not normative product documentation, an
RFC, a compatibility decision, or authorization to change runtime, routing,
CLI, configuration, API, privacy, or failure behavior.

The validation used public, documented operator surfaces rather than
source-level proof scaffolding. `caller` and `receiver` below are neutral roles;
private hostnames, LAN addresses, paths, prompts, generated responses, account
details, credentials, and unnecessary hardware details are intentionally not
retained.

PR #619, “Investigate Home AI Cluster 1.0 CLI contract candidate,” merged as
`7d6a183242457d00cc5dc1ffaeb1cf40850cad91`. Its conclusion was that the CLI
was ready to enter final fresh-install/two-node operator validation, but not
yet ready for the final 1.0 compatibility promise. This record does not reopen
those compatibility decisions.

The test did not validate the final published-package path:

```text
uv tool install home-ai-cluster
```

Installation and upgrade validation must be repeated against the actual
published candidate or release distribution before 1.0.

The caller was Debian/aarch64 with Ollama and candidate HAC `0.9.0.dev0`; its
retained local routing capability was constrained to `chat`, and it retained
one remote node declaring `summarize`. The receiver was Ubuntu/x86_64 with
Ollama and candidate HAC `0.9.0.dev0`, with its local runtime configured
through retained configuration.

## Retained-configuration proof

Retained configuration was created through ordinary CLI surfaces, including
the normalized forms:

```text
hac config local \
  --runtime ollama \
  --ollama-model llama3.2 \
  --local-capability chat

hac config node <remote-node> \
  --base-url http://<receiver-lan-address>:25042 \
  --capability summarize
```

`hac config show` confirmed caller-local `chat`, one remote node with
`summarize`, the Ollama local runtime/model configuration, and that automatic
Chat external-information fallback was not authorized. No real remote URL is
retained here.

## Successful proofs

All observations in this section are PASS results.

### Ordinary receiver startup

The receiver successfully started ordinary HAC LAN service with the equivalent
of:

```text
hac local --host 0.0.0.0 --port 25042
```

### Retained static cluster and capability routing

The caller successfully started `hac static-cluster` with no `--declaration`,
`--remote-node-id`, or additional topology/runtime arguments. This proves that
ordinary `static-cluster` consumed retained topology.

Real JSON requests returned cluster-owned attribution. The retained routing
conclusion was:

```text
chat      -> local
summarize -> remote
```

The test deliberately does not retain the prompts or generated content.

### Retained topology restart

Both HAC processes were stopped and restarted without any additional `hac
config` command. The receiver ordinary HAC and caller `hac static-cluster` were
restarted; a subsequent summarize request again routed to the retained remote.

**Conclusion:** retained two-node topology survived process restart and was
reused automatically.

### Remote HAC receiver failure and recovery

The receiver HAC process was stopped while caller `static-cluster` remained
running. A remote summarize request failed with bounded caller output and exit
status 1:

```text
error: runtime adapter unavailable
```

There was no hidden local fallback, no implicit retry, and the caller process
remained alive. After the receiver HAC was restarted, the same caller process
recovered without restart and summarize again routed remotely. The functional
failure/recovery behavior is PASS; O-10 records the wording friction.

### Remote runtime-only failure and recovery

With receiver HAC still alive, its external Ollama runtime was stopped. Receiver
health retained the intentional declared-versus-observed distinction:

```text
Declared state:
  Availability: available
  Healthy: true

Adapter observation:
  Status: unavailable
```

A caller remote summarize request then returned:

```text
error: ordinary request failed
exit=1
```

After Ollama restarted, while both HAC processes remained running, remote
summarize again succeeded with remote attribution and receiver health again
observed the adapter as available. Runtime recovery is PASS; O-11 and O-12
record the clarity and wording findings.

## O-13 — observed ASGI traceback leak

**Classification:** high-priority candidate blocker.

During the expected remote-runtime-unavailable test, receiver HAC was
reachable but receiver Ollama was unavailable. Caller `hac static-cluster`
emitted a full ASGI exception traceback. It exposed categories of internal
information including local Python filesystem paths, the remote LAN target, the
internal endpoint `/internal/cluster/request`, HTTPX/HAC implementation
classes, and stack frames. The traceback itself is not reproduced.

The observed exception chain included an HTTP 503 response,
`httpx.HTTPStatusError`, and cluster `RemoteTransportError`. An initial
code-path observation made during validation was that
`HttpRemoteTransport.send()` calls `response.raise_for_status()`, the remote
503 is translated to `RemoteTransportError`, and the summarize cluster request
boundary was observed to normalize `RuntimeAdapterUnavailableError` and
`NoSelectableRoutingCandidateError`, but not that `RemoteTransportError`.
The exception therefore appeared to escape to Uvicorn/ASGI logging.

This is not a final root-cause determination. It requires dedicated
reproduction and investigation. A later apparently contradictory Uvicorn
access-log line showed `200 OK` for `POST /v1/summarize`; this must not be
interpreted until the dedicated O-13 investigation reproduces and explains it.

O-13 remains a candidate 1.0 blocker until it is understood and corrected, or
otherwise resolved against accepted contracts. This record proposes no fix.

## Overall validation verdict

The core architecture was validated successfully on two real machines. The
proof demonstrated retained configuration, ordinary static multi-node topology,
local and remote capability routing, actual node attribution, process-restart
persistence, remote HAC receiver failure and recovery, remote runtime failure
and recovery, no hidden local fallback, and bounded caller failures.

The multi-node architecture was not invalidated. The candidate is nevertheless
not ready for a final 1.0 declaration because validation exposed unresolved
pre-1.0 work. Current follow-up priority, recorded rather than newly planned,
is:

1. O-13 — remote expected-failure traceback leak.
2. O-08 — retained configuration versus preflight/status workflow.
3. O-14 — bare config discovery.
4. O-10/O-12 — failure wording.
5. Documentation findings O-01/O-02/O-06/O-07/O-11.

## Non-normative follow-up and remaining validation

The next work should be separate focused changes: a dedicated O-13
investigation with no implementation until classified as an accepted-boundary
defect or an RFC question; a separate O-08 investigation; a later O-14 CLI
discovery audit; documentation cleanup after contract questions are resolved;
and final published-package installation/upgrade validation before 1.0.

This proof does **not** establish final-package installation from a published
1.0 candidate, truly fresh installs on both machines, final Windows installation
experience, final 1.0 compatibility-policy decisions, every command/capability/
failure combination, Internet-facing operation, discovery, scheduling, load
balancing, dynamic topology, or runtime lifecycle ownership.
